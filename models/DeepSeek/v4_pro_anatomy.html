DeepSeek-V4-Pro 架构解剖

61 层文本骨干，隐藏维 7168，每层一条 512 维的 MQA latent。 注意力按 compress_ratios 分成两种并严格交替：31 层 HCA（128 个 token 压一行，全看） 与 30 层 CSA（4 个 token 压一行，indexer 选 top-1024）。 残差是 4 路宽的 mHC，前 3 层的专家不由门控选而是查哈希表，末尾挂 1 层 MTP。

先分清对象

一份 config 里只有两个开关，但它们决定了全部

架构名是 DeepseekV4ForCausalLM，model_type 为 deepseek_v4，纯文本、无视觉塔。 真正决定这个模型长什么样的是 compress_ratios 和 num_hash_layers 两个字段： 前者逐层给出「多少个连续 token 压成一行 KV」，后者说前几层的专家不按门控选。 下面的形状与字节来自 64 个 safetensors 分片的头部（共 145 116 个张量）： 逻辑参数按权重元素计，FP4 的一个 I8 字节算 2 个参数，.scale 不进参数量。

compress_ratios：0 / 4 / 128

  • 128 = HCA（31 层）：128 个 token 压成一行，不做 top-k，把所有压缩行全看一遍。
  • 4 = CSA（30 层）：4 个 token 压成一行，再由 indexer 从中选 index_topk = 1024 行。
  • 0 = Dense：只有滑窗。骨干里一层都没有，只有 MTP / 草稿层是这一档。
  • 排布是严格交替的：层 0、1 是 HCA，之后 CSA 与 HCA 一层隔一层，直到层 60（CSA）。

其余三件事

  • 每一层都另有自己的 128 token 滑窗，与压缩行是两份不同的 KV。
  • 残差从 embedding 起就是 [T, 4, 7168]；每个子层用 FP32 的 hc_*_fn [24, 28672] 预测 pre / post / 4×4 混合，Sinkhorn 20 步。
  • MoE 固定 384 选 6 加 1 个共享专家；层 0 / 1 / 2 的选择来自 tid2eid[input_ids]，而不是门控 logits。

和 V4.1-Flash 是同一套字段，不同取值

V4.1-Flash 的 compress_ratios 只允许 0/1/2，并引入了 KV owner： 40 层里只有 4 层写压缩 KV，其余层借用。V4-Pro 没有 owner 这一层间接 —— 每个 HCA/CSA 层都自己压、自己写、自己读，CSA 层还各自跑一次 top-1024。 两代共有的是：MQA 单 KV 头、512 维 latent、尾 64 维 RoPE、分组输出 LoRA、attn_sink、4 路 mHC、sqrtsoftplus 路由。

V4-Pro 与 V4-Pro-0813

两份 checkpoint 的骨干完全相同。差别只在尾巴：DeepSeek-V4-Pro 是 1 层 MTP （num_nextn_predict_layers = 1），-0813 把它换成 3 层 DSpark （dspark_block_size = 5，dspark_markov_rank = 512，输入取层 58/59/60）， compress_ratios 也相应多出两个 0。

主结构 · 层调度

HCA 和 CSA 一层隔一层，61 层里没有一层是稠密的

compress_ratios 一共 62 项：前 61 项给骨干，最后一项给 MTP 层。 骨干的排布是 [128, 128, 4, 128, 4, …, 128, 4] —— 层 0 和层 1 连着两个 HCA， 从层 2 起 CSA 与 HCA 严格交替，层 60 以 CSA 收尾。 数下来是 31 个 HCA 和 30 个 CSA，一个 Dense 都没有。

1 M 上下文下，两种层看到的行数天差地别

同样是 1 048 576 个 token 的历史：HCA 层把它压成 8192 行，然后一行不落全读； CSA 层把它压成 262 144 行，然后只读 indexer 选中的 1024 行。 两者读的行数是 8192 对 1024，但前者的每一行代表 128 个 token、后者代表 4 个。 粗看全局和细看局部，这就是交替排布要买的东西。

滑窗是第三份，和上面两份都不一样

不管哪种层，都另有一条 sliding_window = 128 的环，存的是没压过的原始 latent。 所以一个 CSA 层的 query 实际看到的是「最近 128 个原始 token」加「从历史里挑出来的 1024 行压缩块」， 两份 KV 物理上在同一个池子里，但一个按 slot 寻址、一个按 block 寻址。

Attention 块 · 合并

1152 行不是两次注意力，是一次 softmax

滑窗行和压缩行被拼进同一份 CSR 索引表，交给同一个 kernel。 没有门控，没有加权合并，两类行在 softmax 里平等竞争。 能这样做的前提是它们在池子里结构同构：都是一条 [512] 的 latent， 而且 K 和 V 是同一行 —— kernel 只收一个 KV 张量。

三种层只有行数不同

Q 和 KV 的维度三种层完全一样：[1, 128, 512] 对 [N, 512]。 变的只是 N —— CSA 是 ≤1024+128，HCA 是「全部 (pos+1)/128 行 + ≤128」（1 M 上下文 = 8192+128）， Dense 只剩 ≤128。同一个 kernel、同一条输出通路。

prefill 是两源，仍是一次 softmax

prefill 走 sparse_attn_v4_paged_prefill，收两套 indptr：prefix（池子里前面 chunk 的滑窗 + 压缩行） 和 extend（本 chunk 还没进池的 K）。kernel 内部按 flash 的方式分段算再用 log-sum-exp 归并， 数学上仍是对 prefix ∪ extend 这一个集合的一次 softmax。

特殊模块 · compressor

HCA 一个，CSA 两个，宽度差在 overlap

compressor 接在 Attention 块的 hidden 侧面，不经过 wqkv_a。 HCA 把 128 个 token 压成一行，组与组不重叠。CSA 的主 compressor 打开 overlap： 每行池化的窗口是 2 × ratio = 8 个 token，相邻两行重叠一半，所以投影从 512 宽变成 1024。 indexer 自己还有一个更窄的 compressor，它的输出只用来打分。

特殊模块 · indexer

CSA 的 top-1024 是在一份独立的、压得更狠的 KV 上选出来的

indexer 不在主 KV 上打分。它有自己的 compressor（head_dim = 128）， 把同样 4 个 token 一组压成一行 128 维的 index key，写进另一个池子； query 侧也单独投影成 64 头 × 128 维。打分完只输出行号，真正的 KV 仍从主池取。

indexer 的 Q 不切 TP

indexer.wq_b 是 ReplicatedLinear：64 个头在每个 rank 上都要有。 理由很直接 —— 打分要对 64 个头求和才得到一个 logit，切了就得为 index_score 再加一次 all-reduce。 这张表只有 12.58 M，复制一份比多一次通信便宜。

index KV 的精度是单独的开关

原生单节点默认 FP4（gfx942 例外，仍 FP8），插件路径保持 FP8。 --index-cache-dtype fp8 可以强制回退。 gfx950 与 gfx1250 的 FP4 布局故意不兼容：前者是 pa_mqa_logits_fp4 的预洗牌布局，后者是 OPUS 自然行 —— 所以 indexer_layout 要和 quant_mode 分开记，一个说怎么量化，一个说怎么摆。

rotate = True 是个还没接上的标志

Compressor.__init__ 收一个 rotate 参数，indexer 那份传的是 True。 但 rotate_activation（atom/model_ops/quant_v4.py 的 Walsh-Hadamard） 在整个 V4 路径里没有任何调用者 —— 全仓只有 GLM-5.3 的 k-pool 和 V4.1 的融合 RoPE 用到 Hadamard， 后者还显式传 do_rotate_act=False。 源码注释说明了它是给后续 PR 留的判别位：参考实现训练时做的是 rotate_activation(kv) 再 FP4 量化的 QAT 往返，这一步目前没有移植。 看到这个标志不要当成「跑了 Hadamard」。

稀疏要到 4K 之后才真的生效

CSA 的候选行数是 (pos+1)/4，要超过 index_topk = 1024 才会丢东西 —— 也就是 pos ≥ 4095。在那之前 top-1024 选中的是全部候选行， CSA 层等价于「滑窗 + 全部压缩历史」。 4K 以内的 benchmark 测不到这套机制的稀疏行为，只测到它的压缩损失。

打分读的字节和它要剪枝的那次注意力差不多

同样在 pos = 20000：打分要扫 5000 行 index K，FP8 下 5000 × 132 B ≈ 660 KB； 而被它剪到 1024 行之后，注意力读主 KV 是 1024 × 640 B ≈ 655 KB。 换成 FP4 index 平面（68 B/行）降到 340 KB，约为注意力的一半 —— 这大概就是原生单节点默认选 FP4 的原因（recipe 写了 gfx942 除外）。 只是字节数对比，不是时延对比；两者访存模式不同，没有实测。

压缩器状态环比滑窗还大

每请求、每层、FP32、kv_state 与 score_state 各一份： CSA 主环 (8, 1024) = 64 KiB、CSA index 环 (8, 256) = 16 KiB、 HCA 主环 (128, 512) = 512 KiB。 合计约 17.8 MiB / 请求，其中 HCA 占 15.5 MiB —— 比 FP8 滑窗的 4.77 MiB 还大 3.7 倍。 HCA 环必须 128 深，因为它的池化窗口就是 128，跨 forward 边界时最多要补 127 个历史位置。

特殊模块 · mHC

残差一路是四路宽的，每个子层进出都要过一次 Sinkhorn

embedding 进第一层之前被展成 [T, 4, 7168]。每个子层（注意力、FFN 各算一个）做两件事： hc_pre 把 4 路残差按预测出来的权重收成一路 [T, 7168] 喂给子层， hc_post 把子层输出按另一组权重摊回 4 路，同时用一个 4×4 组合矩阵重新混合旧残差。 这两组权重和那个矩阵都是同一个投影出来的，再经 20 步 Sinkhorn 投影到双随机流形上。

图 4 · KV 池

一个行空间，两头生长：历史按块、滑窗按槽

V4 把两种 KV 放进同一个行空间：压缩历史按 block 寻址，从 0 往上长； 每请求的滑窗和压缩器状态按 slot 寻址，从高位往下长。 「一行」在所有平面上指同一个意思，但一行的字节数各平面不同 —— 这是硬要求， 因为稀疏 kernel 拿的是一份共享的 index 缓冲区，NoPE 和 RoPE 两个平面必须用同一个行号。

为什么 NoPE 和 RoPE 不能是同一个信封的两段

假设一个信封 E 字节，那么块 b 的第 r 行在一个平面上是 b·E/512 + r， 在另一个平面上是 b·E/128 + r —— 两者只有在 E = 0 时才相等。 而 mla_decode_fwd_v4_nm 这类 kernel 只收一份 index 缓冲区， 所以两个平面必须各自是一张密排的平面，行号才能通用。

MQA 单 KV 头 = KV 不随 TP 分摊

num_key_value_heads = 1，所以 TP8 不会把 KV 切成 8 份： 上面那 5465 B/token 是每个 rank 都要存一份的量。 省显存的开关因此是 --kv_cache_dtype fp8（1024 → 640 B/行）和 FP4 index 平面，而不是加 TP。

怎么跑起来

recipe 给的是 8 × MI355X、TP8、FP8 KV： AITER_BF16_FP8_MOE_BOUND=0 ATOM_MOE_GU_ITLV=1 加 --kv_cache_dtype fp8 -tp 8。 不需要 --trust-remote-code，DeepseekV4ForCausalLM 是 ATOM 内置架构。 这个配置在 MI355X / gfx950 上测得 GSM8K（1319 题，3-shot flexible-extract）0.9522。

可选的 EP / DP 路线

--enable-expert-parallel --enable-dp-attention --all2all-backend rccl 走原生 RCCL 的专家派发： 均匀 decode 用图安全的预路由 AllGather/ReduceScatter 快路径，prefill 与混合批走变长版本。 它只消费既有路由产出的物理专家 ID，不改 EPLB 策略；TBO 在这个后端上不支持。

形状与参数来自 deepseek-ai/DeepSeek-V4-Pro 的 64 个 safetensors 分片头部（145 116 个张量，落盘 805.32 GiB）， 逐层类型与 compress_ratios 来自同仓库的 config.json。 scale 不计入参数量；FP4 按解开后的逻辑元素计数。 层行为、kernel 与量化口径对照的是 ATOM main a526f0d55（2026-10-07）的 atom/models/deepseek_v4.py 与 atom/model_ops/attentions/pool_layout/。 KV 的 1982 行 / 信封（原生块大小 256）与 7808 行 / 请求是直接实例化 UnifiedPoolGeometry 得到的，字节数由各平面的行宽换算。
