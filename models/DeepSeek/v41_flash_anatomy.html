DeepSeek-V4.1-Flash 架构解剖

40 层文本骨干，隐藏维 5120，单层一条 512 维的 MQA latent。压缩比只有 0、1、2： 2 层纯滑窗，18 层把 2 个 token 收成 1 行，20 层一行对一个 token。 残差是 4 路宽的，层 1 和层 14 各插一张宿主机上的 Engram 表，末尾 3 层 DSpark 用同一份 checkpoint 起草。 注意力按 WINDOW / FULL / REINDEX / REUSE 分成四种，Q 和输出投影四种一模一样， 差别只在「写哪几份缓存」和「top-512 从哪来」。

先分清对象

一份 checkpoint 里叠了四套机制

架构名是 DeepseekV41ForCausalLM，model_type 为 deepseek_v41。 文本配置在 text_config（deepseek_v41_text），视觉塔在 vision_config。 ATOM 的 normalize_hf_config 把文本字段摊平给骨干，同时保留一份独立的多模态根配置。 下面的数字来自 48 个 safetensors 分片的头部：逻辑参数按权重元素计，FP4 的一个 I8 字节算 2 个参数，.scale 单列、不进参数量。 按这个口径把全部张量的存储字节加总，等于索引里的 total_size = 510,286,023,000。

CSA2 注意力

  • 每个 token、每一层先投影出一条 [512] latent。64 个 query 头各是 [512]，KV 头数是 1。
  • RoPE 只转 latent 和 query 的最后 64 维。前 448 维是 NoPE。滑窗用 rope_theta = 10000；压缩行用 compress_rope_theta = 160000 的 YaRN（factor 16，原长 65536）。
  • 每一层都有自己的 128-token 滑窗。压缩层再额外看所属 KV owner 上最多 512 行压缩 KV。

mHC、Engram、DSpark

  • embedding 在进第一层之前被复制成 [T, 4, 5120]。每个子层用 FP32 的 hc_*_fn [24, 20480] 预测 pre / post / 4×4 混合，Sinkhorn 20 步。
  • Engram 在层 1、层 14，表在宿主机 mmap。层 1 的表是 [384006168, 256] FP8，层 14 是 [384016682, 256]。
  • DSpark 三层只做滑窗，专家缩小到 128 选 3，一次起草 5 个 token。输入取层 37、38、39 的残差均值。

四种模式在磁盘上差哪些张量

WINDOW 与 REUSE 没有 compressor，也没有 indexer。 REINDEX 有 indexer.wq_b 和 weights_proj，没有 indexer.wk。 FULL 才有 compressor.wkv、indexer.wk 和 k_norm。 ratio 2 的 FULL 层（2、8、14）多一个 compressor.wgate [512, 5120]；ratio 1 的层 20 没有这张门。

主结构

从 token 到 logits，注意力是其中一块

文本骨干一次前向的模块顺序是固定的。Attention 在这里是一块：进去是 mHC 之后的 [T, 5120]，出来还是 [T, 5120]。四种内部结构在下一节。 Engram、mHC、MoE、DSpark、视觉塔在主图里也先收成块，形状写在块上，内部见后面的单独拆解。

Attention 块

这块里面，40 层走的是同一条投影通路

主结构里那块 Attention 拆开之后，是下面这条链。四种模式的差别不在这条链上： build_attention_topology 只决定这一层额外带哪些权重、 往哪几份缓存写、top-512 从哪来。 compressor 与 indexer 接在链的侧面，它们是特殊模块，不画进这条主链。

Attention 块 · 四种内部结构

同一套 Q/O，四种「写什么、读什么、谁打分」

上一张图是主结构里那块 Attention 的内部。下面四张只标每种模式多出来的权重、写入和读取。投影路径四种相同：wqkv_a 一次 GEMM 出 q_lora [T, 1280] 与 kv [T, 512]， DualRMSNormMXFP8 一次归一化并顺手把 qr 量化成 FP8，wq_b 展开成 Q [T, 64, 512]， 输出端一律是「逆 RoPE 融合分组量化 → wo_a 8 组 → wo_b」。 build_attention_topology 给每层贴的标签只决定三件事：这一层额外带哪些权重、 往哪几份缓存写、top-512 从哪来。 40 层里有 30 层既不压缩也不打分。

这四个标签是算出来的，不是配置里写死的

配置只给三样东西：compress_ratios、kv_source_layer_ids、index_source_layer_ids。 build_attention_topology 从前往后扫：ratio 为 0 判 WINDOW；否则沿用最近一个 KV owner， layer_id == kv_owner 判 FULL，layer_id == topk_owner 判 REINDEX，剩下的是 REUSE。 校验也在这里：每个 KV source 必须同时是 index source，window-only 的层不能当 owner，候选块要能装下一整个 top-k。

所以「稀疏」省在哪

省的不是注意力本身的行数 —— 四种模式读的都是「≤128 滑窗 + ≤512 压缩行」这个固定预算。 省的是造 KV 的次数（40 层只有 4 层写）和打分的次数（40 层只有 8 层算，其中 4 层还被夹在 16 384 行里）。 1 M 上下文下，注意力每层读的行数是常数，这是 CSA2 的整个要点。

四种层合并出来的是什么形状

不管哪种模式，滑窗行和压缩行都被拼进同一份 CSR，进同一次 softmax，没有门控也没有加权合并。 decode 一个 token 的形状是 Q [1, 64, 512] 对 KV [N, 512] —— num_key_value_heads = 1，64 个 query 头共用同一份 N 行，而且 K 和 V 是同一行（kernel 只收一个 KV 张量）。 N 最多是 128 滑窗 + 512 压缩 = 640，WINDOW 层只有 ≤128。 attn_sink [64] 每头一个，只进 softmax 分母。

出来之后

out [1, 64, 512] → 逆 RoPE（在 query 自己的位置上转回去，因为 K = V 且 V 是旋转过的） → wo_a 8 组 × [1024, 4096] → [1, 8192] → wo_b [5120, 8192] → [1, 5120]。 inverse_rope_group_quant 把逆 RoPE 和 wo_a 的 per-32 分组量化融成一发，省一次 BF16 往返。

CSA2 的池化比 V4 简单一截

同一个 fused_compress kernel，但 CSA2 从不重叠（compress_ratios 恒返回 (ratio, False)）：ratio 2 的一行只池化 2 个 token，ratio 1 根本不池化。 所以没有 V4 那套「同一个 token 在两行里用不同半边列」的角色切换，投影宽度就是 head_dim。 池化本身仍是逐通道的 softmax —— (values * scores.softmax(dim=2)).sum(dim=2)， softmax 沿组内位置，每个通道独立。

ape 在这里是一串零

V4 给池化的门加了一个学出来的组内位置偏置 ape（checkpoint 里是真张量）。 CSA2 不用它，但为了共用同一个 kernel，仍然挂了一个全零的 register_buffer("ape", ..., persistent=False) —— 不在 checkpoint 里，也不会被当成未加载的参数报警。 反过来说：compressor.ape 在不在 safetensors 里，是区分 V4 与 V4.1 谱系的一个便宜判据。

特殊模块 · compressor

只有 FULL 层有它，ratio 1 和 ratio 2 差一个门

compressor 从 Attention 块的 hidden 侧面分出去，不经过 wqkv_a。 它写出的是 owner 平面上的压缩行；indexer 吃的是 RoPE 之前的那份 latent。 CSA2 的组与组不重叠（overlap = False），半成品留在每请求的 FP32 ring 里，不进 PAGE。

特殊模块 · 压缩平面与候选块

4 个 owner 的平面，8 个层负责打分

特殊模块 · indexer

top-512 是怎么从一个分页平面里选出来的

打分从来不把 key 重新物化出来：query 量化之后直接交给分页 MQA logits kernel， 平面本身就是 PAGE 里那块 index 区域。每一个 query 行都是自己的一个「批次项」， 带自己的可见长度和自己的块表 —— 所以 prefill 的 token、decode 的 token、草稿的 token 在打分器眼里是同一种行， ragged 批次对它不构成特殊情况。

visible 是每行自己的前缀长度

打分器要求可见性是「一个前缀」，不是一张掩码。一行看不到的列压根不被读，也不被写 —— 所以 selected 里的 -1 不是「选了个空」， 而是「这一行的历史还不够 512 行」。下游的 _indptr_scan 据此用闭式公式 min((pos+1)/ratio, 512) 直接算出每行占多少格，不用真去数一遍。

FP8 与 FP4 平面的区别只在字节

--index_cache_dtype 选 fp8（默认）或 fp4，选哪个都不改变上面这条链路的形状， 只改变 key 的落盘格式、query 的量化方式，以及一件实质的事：平面精度不同，选出来的行就不同。 值得记一笔：V41PoolGeometry.layout_id —— 前缀复用和 lmcache_mp 状态键都按它匹配 —— 里那一段目前是写死的 index-fp8，注释也还停留在「FP8 是唯一平面」的年代， 所以换成 fp4 平面并不会改变这个串。

图 6 · KV

历史走 PAGE，滑窗和半成品组走 STATE

默认池是 BF16 主平面加 FP8 index（--kv-cache-dtype auto / bfloat16）。 页大小在 vLLM 插件里固定为 ATOM_DEEPSEEK_V41_BLOCK_SIZE = 256。 下面的字节数是 V41PoolGeometry 对这份 config 的结果：paged_bytes = 739840，正好是 256 × 2890。

换成 packed FP4 主池

nvfp4 把主平面改成每行 288 B（512 维 E2M1 加 group-16 的 E4M3 scale），滑窗行变成 528 B（512 个 FP8 加 16 个 E8M0）。 index 平面不受这个开关影响。按同样的 4 个 owner 摊下来是 1050 B/token，一页 268 800 B。 主池只认 bf16 和 fp4 两种，没有单独的 FP8 KV 池。 index 平面是另一个开关 --index_cache_dtype：fp8（默认，132 B/行）或 fp4（68 B/行）， 后者把 BF16 池压到 2730 B/token，把 packed 池压到 890 B/token。

DSpark 要求 BF16 KV

投机配置一旦打开，kv_cache_dtype 必须是 bf16，草稿宽度必须是 5，方法名必须是 dspark，而且草稿模型和目标模型是同一份 checkpoint。 另外：main 上的 validate_runtime_config 直接拒绝 plugin mode —— V4.1 目前只有 ATOM 原生这一条执行路径，vLLM 插件桥接（页大小固定 256、STATE 另占 proxy block）还在未合入的分支上。

会被直接拒绝的

  • pipeline / context / data parallel，TBO，EPLB，RapidServe。V4.1 只跑 TP（专家可整块 EP，也可切 TP）。
  • vLLM 插件模式、在线量化。
  • kv_cache_dtype 不是 bf16 或 fp4；index_cache_dtype 不是 fp8 或 fp4。
  • PAGE 的 token 数是奇数（ratio 2 要能整除）。
  • KV 传输不是 lmcache_mp：只有它会把 STATE 一起过一遍 PAGE 备份；只搬 PAGE 的 connector 拿不到压缩 ring 和游标。
  • 投机不是 dspark / 不是 5 个 token / KV 不是 bf16 / 开了宽松 MTP 验证。

旁路流是可选的，默认一条都不开

ATOM_DSV41_SIDE_STREAMS 取 0 / 1 / 2，默认 0：compressor 和 indexer 都排在主流上，Attention 块的主链、compressor、indexer 三支是顺序执行的。 1 让 compressor 借 MoE 那条 alt_stream（它的生命期在打分处就结束，早于共享专家发出，不额外占队列）； 2 再给 indexer 一条自己的流 —— 只有它会和别的分支同时在飞，所以只有它值一个硬件队列。 把 indexer 挪开本身不赚钱，赚的是另一边：query 投影和那次融合的 rope/window 不再堵在它前面。

mono：把一层压成两个 kernel

ATOM_MONO_ENABLE 默认是 1，针对 ≤ 12 行的 decode（DSpark 的验证步和草稿骨干）： K1 从 mHC 的缝一路做到旋转好的 query 和滑窗行；K2 把打分、稀疏 decode、输出投影、它的 all-reduce、FFN 的缝和 MoE 全放进一次发射 （ATOM_MONO_CHECK 可以把 K2a/K2b 拆开逐段对比）。compressor 和 Engram 仍由原模块在两个 kernel 之间跑。 注意：它目前会被拒绝 —— 里面的 MoE kernel 还在跑 MXFP4 激活，而 V4.1 的路由专家要的是 MXFP8。

为什么路由专家必须喂 MXFP8

专家权重是 FP4，但激活不是。aiter 在 gfx950 上对这种专家的默认是 MXFP4 激活， 那样算出来的路由输出比参考实现偏 ~12%，GSM8K 掉约 1.4 pp。 moe.py 因此显式把 moe_fp8_activations 钉成 True。 这也是上面 mono 被拒的同一个原因。

权重进哪一块内存

骨干和视觉走通用的 load_model。Engram 表在 weights_mapper 里被映成空，不注册成参数，由 model_loader/deepseek_v41.py 的 mmap 一直持有。 DSpark 是另一个模块，只在投机打开时再扫同一份 checkpoint 里的 mtp.*。

和字节相关的拒绝

  • 压缩比出现 0/1/2 以外的值，或者草稿层的 ratio 不是 0。
  • 候选块装不下 512 个选中行。
  • 量化格式不是上面那一套 native FP8 + FP4。
  • KV 传输只搬 PAGE、不搬 STATE。这样的 connector 会被拒绝，而不是降级运行。
