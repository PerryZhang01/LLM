DeepSeek-V4.1-Flash 架构解剖

40 层文本骨干，隐藏维 5120，单层一条 512 维的 MQA latent。压缩比只有 0、1、2： 2 层纯滑窗，18 层把 2 个 token 收成 1 行，20 层一行对一个 token。 残差是 4 路宽的，层 1 和层 14 各插一张宿主机上的 Engram 表，末尾 3 层 DSpark 用同一份 checkpoint 起草。

先分清对象

一份 checkpoint 里叠了四套机制

架构名是 DeepseekV41ForCausalLM，model_type 为 deepseek_v41。 文本配置在 text_config（deepseek_v41_text），视觉塔在 vision_config。 ATOM 的 normalize_hf_config 把文本字段摊平给骨干，同时保留一份独立的多模态根配置。 下面的数字来自 48 个 safetensors 分片的头部：逻辑参数按权重元素计，FP4 的一个 I8 字节算 2 个参数，.scale 单列、不进参数量。 按这个口径把全部张量的存储字节加总，等于索引里的 total_size = 510,286,023,000。

CSA2 注意力

  • 每个 token、每一层先投影出一条 [512] latent。64 个 query 头各是 [512]，KV 头数是 1。
  • RoPE 只转 latent 和 query 的最后 64 维。前 448 维是 NoPE。滑窗用 rope_theta = 10000；压缩行用 compress_rope_theta = 160000 的 YaRN（factor 16，原长 65536）。
  • 每一层都有自己的 128-token 滑窗。压缩层再额外看所属 KV owner 上最多 512 行压缩 KV。

mHC、Engram、DSpark

  • embedding 在进第一层之前被复制成 [T, 4, 5120]。每个子层用 FP32 的 hc_*_fn [24, 20480] 预测 pre / post / 4×4 混合，Sinkhorn 20 步。
  • Engram 在层 1、层 14，表在宿主机 mmap。层 1 的表是 [384006168, 256] FP8，层 14 是 [384016682, 256]。
  • DSpark 三层只做滑窗，专家缩小到 128 选 3，一次起草 5 个 token。输入取层 37、38、39 的残差均值。

规模

763.21 B 逻辑参数，单 token 碰 16.79 B

参数量的大头是两块稀疏存储：40 层 × 384 个 FP4 路由专家，加上两张 Engram 表。 单 token 激活按「这一步真正参与乘加的权重」计：6 个路由专家加 1 个共享专家、全部注意力、embed 与 lm_head。 Engram 表每个 token 只 gather 24 行，不计入激活；视觉塔和 DSpark 是另外的前向。

16.79 B 是怎么凑出来的

  • 路由专家 8.49 B — 40 层 × 6 × 35.39 M
  • 注意力 5.08 B — 40 层全部参与，另加 compressor 18.4 M、indexer 43.5 M
  • 共享专家 1.42 B — 每层 1 个，FP8
  • embed + lm_head + 最终 norm 1.32 B
  • Engram 投影 0.31 B — 两层的 wkv 整矩阵都乘
  • 路由门 + mHC 0.099 B

三笔存储不要混

  • 骨干 GPU 权重 278.12 GiB：注意力、MoE、embed、Engram 投影。两张表、视觉塔、DSpark 都不在这笔里。
  • Engram 表 188.83 GiB，宿主机 mmap，按 FP8 行存。按 float32 展开单层大约 393 GB，所以 gather 之前不做全表反量化。
  • 另外两笔：视觉塔 0.90 GiB，挂在多模态模型上一起加载；DSpark 7.39 GiB，只在打开草稿时从同一份 checkpoint 再读。落盘合计 475.24 GiB。路由专家占逻辑参数的 71%，占磁盘大约 57%。

四种模式在磁盘上差哪些张量

WINDOW 与 REUSE 没有 compressor，也没有 indexer。 REINDEX 有 indexer.wq_b 和 weights_proj，没有 indexer.wk。 FULL 才有 compressor.wkv、indexer.wk 和 k_norm。 ratio 2 的 FULL 层（2、8、14）多一个 compressor.wgate [512, 5120]；ratio 1 的层 20 没有这张门。

一个 query 实际能看到的行

decode 的前缀长度是闭式的：滑窗行数（最多 128）加上 min((pos+1) / ratio, 512) 行压缩 KV。 ratio 0 的层没有第二项。prefill 里，当前 chunk 的本地 token 走 extend 段，避免本 chunk 的滑窗写覆盖还没读完的行。

REUSE 为什么不用再算一遍

同一段里的层共享一次打分。段的第一层就是 top-k owner，它先把 selected 写进本步的 step。 后面的层按 index_group_start 取已经写好的下标，decode 时整段的下标一次建完。

默认池是 BF16 主平面加 FP8 index（--kv-cache-dtype auto / bfloat16）。 页大小在 vLLM 插件里固定为 ATOM_DEEPSEEK_V41_BLOCK_SIZE = 256。 下面的字节数是 V41PoolGeometry 对这份 config 的结果：paged_bytes = 739840，正好是 256 × 2890。

换成 packed FP4 主池

nvfp4 把主平面改成每行 288 B（512 维 E2M1 加 group-16 的 E4M3 scale），滑窗行变成 528 B（512 个 FP8 加 16 个 E8M0）。 index 仍是 132 B/行。按同样的 4 个 owner 摊下来是 1050 B/token，一页 268 800 B。 插件路径没有单独的 FP8 KV 池，传入 fp8 会直接报错。

DSpark 要求 BF16 KV

投机配置一旦打开，kv_cache_dtype 必须是 bf16，草稿宽度必须是 5，方法名必须是 dspark，而且草稿模型和目标模型是同一份 checkpoint。 插件路径目前不接 DSpark，也不接视觉塔和跨请求的压缩前缀复用。

权重进哪一块内存

骨干和视觉走通用的 load_model。Engram 表在 weights_mapper 里被映成空，不注册成参数，由 model_loader/deepseek_v41.py 的 mmap 一直持有。 DSpark 是另一个模块，只在投机打开时再扫同一份 checkpoint 里的 mtp.*。

和字节相关的拒绝

  • 压缩比出现 0/1/2 以外的值，或者草稿层的 ratio 不是 0。
  • 候选块装不下 512 个选中行。
  • 量化格式不是上面那一套 native FP8 + FP4。
  • KV 传输只搬 PAGE、不搬 STATE。这样的 connector 会被拒绝，而不是降级运行。

形状与参数来自 DeepSeek-V4.1-Flash 的 48 个 safetensors 分片头部，以及 atom/models/deepseek_v41/weights.py 的 schema。 存储字节复算结果与 model.safetensors.index.json 的 total_size 一致。 层模式、KV 字节和前向顺序来自 atom/models/deepseek_v41/ 与 atom/model_ops/attentions/pool_layout/v41_pool_geometry.py。 scale 不计入参数量；FP4 按解开后的逻辑元素计数。
