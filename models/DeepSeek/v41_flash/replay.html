Bounded Replay

两种 bounded replay 都建立在同一个观察上——后续步骤会读到的才去算：decoder replay 让 prefill 只在每个请求的最后 128 行跑 decoder， encoder replay 让前缀命中时不存状态、退一个 hash 块把它重算出来。存储层的形状和地址在第 10 章；这一章讲 replay 时这些存储哪些只读、哪些在新位置写、哪些在新槽里重建， 并把两种 replay 的做法、例子和代价算清楚，再看关掉之后的 checkpoint 方案。

4 份全局 KV 与 index

main_2/8/14 每页 64 行、main_20 每页 128 行，每行 528 B；index 行按 owner 分区、每行 132 B。前缀命中复用的就是这些页， 一个 block id 同时指 4 个 owner（第 10 章 · PAGE）。

STATE · 随并发增长 · 从不共享

窗口、尾巴、游标

每请求一槽：40 层 ring [40, 128, 528]、compressor 尾巴、cursor [位置, h₃, h₂, h₁]。命中拿不回它们， 所以要么重算（本章），要么从镜像拷回（本章末）（第 10 章 · STATE）。

第 21–39 层在别的行上的输出，以后没人读：decoder 没有自己的全局 KV，它的远程信息全部来自第 20 层压缩的 encoder 输出（总览图 4）。 这就是两种 replay 能省的地方。decoder_replay_unsupported 守着这个前提：第 20 层之后不许再有 KV source，也不许有 Engram（atom/models/deepseek_v41/bounded_replay.py:68）。

decoder SWA bounded replay

完成 prompt 的那次 forward，decoder 只在最后 128 行上跑

默认开启（enable_decoder_swa_bounded_replay，atom/config.py:2021；--no-decoder-swa-bounded-replay 关闭）。 对一个完成 prompt 的 forward，每个请求按下表分工；不是最后一个 chunk 的 forward 只跑 encoder 和第 20 层的压缩，decoder 一个 kernel 都不跑。

计算在哪些行上跑原因
第 0–19 层（encoder）全部行它们写 main_2/8/14，并产出第 20 层压缩的输入
第 20 层的压缩（main_20 + index key）全部行decode 时任何 token 都可能检索到任何位置
第 20–38 层 attention 与 FFN（含写各层 ring）tail：最后 W = 128 行以后只读 ring 的最后 128 行
第 39 层 KV（写 ring）tail同上
第 39 层 query、attention、FFN；LM head最后一行只有它要采样

执行顺序（atom/models/deepseek_v41/runtime.py:384 的 _replayed）：

  1. _EarlyLayers：编译好的一张图，跑第 0–19 层的全部行（atom/models/deepseek_v41/runtime.py:199）。
  2. 第 20 层：mHC 接缝 + _compress_batch，仍是全部行——这是唯一被拆成两半的层（第 7 章）。
  3. DecoderGraph.run（atom/models/deepseek_v41/decoder_graph.py:39）：把每个完成 prompt 的请求的最后 min(len, 128) 行 gather 进固定布局的 tail 缓冲， 跑第 20 层 attention + FFN → _LateLayers（第 21–38 层，atom/models/deepseek_v41/runtime.py:222）→ 第 39 层。
  4. 把第 39 层的输出 scatter 回 forward 里各请求的最后一行，其余行填 0；LM head 只读这些行。

tail 的布局

按 running_bs 排成固定地址

lay_out_tail（atom/models/deepseek_v41/bounded_replay.py:154）按本步的 running_bs 排成 running_bs × 128 行（tail_width，atom/models/deepseek_v41/bounded_replay.py:127）： 完成的请求在前，然后是长度为 0 的填充请求、重复某个真实行的填充行。同一个 running_bs 的步骤地址完全一样，decoder 因此能按桶录成 ReqGraph （ATOM_DECODER_GRAPH_SIZES 默认 1,2,3,4,8,16，atom/utils/envs.py:624）。

什么时候不 replay

decode、warmup、草稿、TBO

replayable 只放行 prefill（atom/models/deepseek_v41/bounded_replay.py:93）；decode、warmup、DSpark 草稿、TBO 微批都跑全部行。 runtime 文档还列了几种不走录好的图、改走 eager 的情形：running_bs 不在列表里、带图像行、FP8 index plane、decoder 读 encoder 带来的选择（docs/deepseek_v41_runtime.md）。

精度代价

这不等价于完整 prefill。每个 decoder 层里 tail 行的窗口截断在 tail 起点（swa_replay_start）；从第 21 层开始，连最后一个 token 的窗口里装的都是 「基于截断窗口算出来的行」，所以最后一个 token 的 logits 和 decode 阶段读到的各层 ring 都与完整 prefill 不同。encoder、压缩 KV 与 decoder 复用的 top-k 选择都是精确的。 文档的说法是 “DeepSeek post-trains on this truncation”。TorchSpec 这类要导出每一行 hidden 的用途必须关掉它。

边界情况

最后一段不足 128 行时，往前挪到 hash 块网格上

最后一个 chunk 可能很短，或者前缀命中后只剩很短的后缀，tail 就凑不满 128 行。BlockManager.replay_start（atom/model_engine/block_manager.py:1847）把起点往前挪， 并对齐到 hash 块：min_final_prefill_rows 在 V4.1 上被设成窗口大小 128（atom/config.py:2778）。 

short = min_final_prefill_rows − (num_tokens − start)       # 128 − 剩余行数
if short > 0:
    start = (start − short) // hash_block_size × hash_block_size

例 1 · prompt 1000，chunk 512

chunk 1 = [0, 512)：encoder + 第 20 层压缩共 512 行，decoder 跳过。chunk 2 = [512, 1000)：488 行 ≥ 128，不用挪；encoder + 压缩 488 行，decoder 第 20–38 层只跑 872–999，第 39 层的 query 只算第 999 行。

encoder SWA bounded replay

前缀命中时不存状态，往前退一个 hash 块把它算出来

前缀命中能拿回 PAGE，但 STATE 不在 PAGE 里：40 层窗口、compressor 半成品、Engram 游标都没有。默认做法（enable_encoder_swa_bounded_replay，atom/config.py:2039） 是让后端声明 StateTransfer.replay()（atom/model_ops/attentions/deepseek_v41/backend.py:403、atom/model_engine/state_runtime.py:96）： 引擎不保存 checkpoint，不为 checkpoint 切 chunk，命中可以落在任意 hash 块边界，replay_start 在命中时先 start −= hash_block_size。

精度代价

重建出来的 128 行，窗口截断在重放起点，所以恢复出来的请求的 logits 与冷启动 prefill 不同，偏差的性质和 decoder replay 一样；它读到的缓存全局 KV 仍是精确的。

叠加

两个功能一起作用：退回的 128 行顺手给了 decoder 一个满 tail

存储读写

replay 时 KV cache 怎么存、怎么用：共享页只读，新位置才写，状态在新槽里重建

两种 replay 都靠同两个开关保证「重算不改缓存」：make_compress_plans(write_from=…) 丢掉起点之前已经结束的组，全局 KV 一行都不重写 （atom/model_ops/v4_kernels/compress_plan.py:328）；swa_write(cached_until=…) 让 ring 里已有的行保持原样（atom/model_ops/attentions/deepseek_v41/cache.py:878）。 下图把每块存储在五种场景下的读写摊开（存储的形状与地址见第 10 章）。

例子 · 命中到 768 的那次 forward（prompt 1000），存储逐项怎么动

  1. 分配：块表前 6 列挂上命中的页（与第 10 章图 5 同一组页 [41, 7, 93, 12, 58, 3]，引用计数 +1）；块 6、7（768–1023）各取一个新页； 取一个新 STATE 槽，cursor 的 3 个历史 id 取 637–639 的压缩 token（Replay.history_ids，atom/model_engine/sequence.py:138）。
  2. 第 640–767 行（重放段）：encoder 各层读共享页里的选中行和 index 行，算出这 128 行，只写新槽的 ring（第 0–19 层，窗口从 640 起）； 第 2/8/14 层落在 768 之前结束的组全部被丢掉，第 20 层同理——共享页里没有一个字节被改。
  3. 第 768–999 行：照常把 main_2/8/14/20 和 index 行写进块 6、7 的新页，encoder ring 接着写，compressor 尾巴写末尾 K_pool 个位置。
  4. tail 872–999：第 20–39 层只在这 128 行上跑，写各自的 ring；第 20 层的 Indexer 对 main_20 的 index 全量打分， 0–767 的行在共享页里，768–999 的行在刚写的新页里。
  5. forward 之后：hash_blocks 只登记块 6（768–895）——块 0–5 本来就登记过，块 7 还没写满；cursor 推进到本次 forward 的末尾。

冷启动 · decoder replay

main_20 每行都写，decoder ring 只写 tail

非最后 chunk：encoder 和第 20 层压缩照常写 PAGE 和 encoder ring，decoder 的 ring 不碰。最后一个 chunk：PAGE 照常写，decoder 的 20 层只把 tail 的 128 行写进各自的 ring—— decode 时它们正好读这 128 行。

回退段 · 同一个请求

不换槽，只读不写

最后一段不足 128 行往回挪时（图 2），挪回来的行在本请求自己的页和槽里已经有了：不重写全局 KV，不改 encoder ring，cursor 退回 forward 起点再推进； 真正新写的只有落在 tail 内的 decoder ring 行。

关掉之后

decoder 关掉就是完整 prefill；encoder 关掉改存 STATE 镜像

--no-encoder-swa-bounded-replay

StateTransfer.copy：存镜像

状态传输换成 copy(layout_id)（atom/model_engine/state_runtime.py:116）。镜像内容是 checkpoint_image_ranges：40 层窗口 + cursor，不含 compressor 半成品 （atom/model_ops/attentions/pool_layout/v41_pool_geometry.py:380）。镜像存在 KV 池自己的 PAGE 单元里、按前缀 hash 建索引， 每个占 ceil(镜像字节 / PAGE 字节) 个单元（atom/model_engine/page_unit_checkpoint.py:64），粗算约 13 个。

V4.1 的状态只能在一次 forward 的最后一个 token处取出（readable_midstep = False），所以想在位置 p 留镜像，prefill 必须在 p 处切一刀， 让某次 forward 恰好结束在那里（checkpoint_cut，atom/model_engine/block_manager.py:2886）。位置由一套梯子决定（checkpointers_at，atom/model_engine/block_manager.py:3022）：

  • 间隔梯级：每 state_checkpoint_interval_tokens 一个，默认 8192（atom/config.py:2011）；设 0 关闭，设 −1 不放间隔梯级。
  • prompt 末尾锚点：在 prompt 末尾往前留出「下一次 forward 至少要带的行数」后的最后一个 PAGE 边界；V4.1 开着 decoder replay 时这个余量至少是 128（atom/model_engine/block_manager.py:2615）。
  • 按需补：某次命中因为没有镜像被拒，补一个（state_checkpoint_demand，默认开）。

vLLM 插件

插件路径上两种都没有：前缀缓存整个被拒绝

插件路径由 vLLM 管块分配。V4.1 声明一个假注意力层，它的 FullAttentionSpec 是一块字节 arena（atom/plugin/vllm/deepseek_v41_bridge.py:914）， PAGE 定死为 256（atom/plugin/vllm/deepseek_v41_bridge.py:60），vLLM 的块号就是 V4.1 的页号；STATE 按请求数计价，只能从块池尾部扣出几块不让 vLLM 分配 （v41_proxy_state_reserve_blocks，atom/plugin/vllm/deepseek_v41_bridge.py:275；补丁在 atom/plugin/vllm/deepseek_v41_state_reserve_patch.py:91）。

enforce_deepseek_v41_constraints（atom/plugin/vllm/platform.py:378）拒绝前缀缓存：vLLM 认为每个被缓存的块边界处后端都留下了可恢复的状态， V4.1 只能在 forward 末尾给出状态，checkpoint 这条路走不通；replay 靠的是 ATOM 自己调度器里的 replay_start，而插件路径用的是 vLLM 的调度器。同一个函数还拒绝一切 KV connector，包括 lmcache_mp。 所以插件上的 V4.1 每个请求都从头 prefill。

读码坑

「replay」这个词在 ATOM 里有两种：DeepSeek-V4 的 bounded replay 退的是 state_replay_tokens（状态的感受野），V4.1 的 encoder replay 退的是一个 hash 块。 replay_start 里两条分支挨着写（transfer.replays 与 state_replay_tokens），读的时候别混。
