Reindex 层

decoder 只有一份全局记忆 main_20，但它不想让 20 层都用同一批 512 行。办法是每 4 层重选一次： REINDEX 层用自己的 index query 去打第 20 层的 index key，只打第 20 层挑好的 2048 个候选块。 打分器和第 20 层是同一个，区别只是把「整个请求的 PAGE 表」换成「只含候选块的紧凑块表」，选完再把列号换算回 token 位置。

分工

query 和头权重是自己的，key、候选和全局 KV 都是第 20 层的

第 24 层是 index source 但不是 KV source，所以拓扑给它 REINDEX（atom/models/deepseek_v41/config.py:137）： kv_owner = 20、topk_owner = 24、candidate_owner = 20。建模块时它拿到一个 Indexer， 但 wk 与 k_norm 只在 FULL 层创建（atom/models/deepseek_v41/attention.py:71），Compressor 也没有。

调用链

和第 20 层走同一个打分器，只在入口换了块表、出口多一步换算

第 1 步 · 翻译

候选块号散在请求的各个 PAGE 里，先翻译成一张紧凑块表

candidates[20] 存的是逻辑块号：请求内第几个 8 行块。打分器要的是物理 tile（index plane 里的位置）和每行能读多远。 _candidate_table_kernel 每个 token 一个 program，把两样一起算出来（atom/model_ops/deepseek_v41/candidate_table.py:28）： 

# ratio 1：一个 PAGE = 128 token = 16 块，每块 8 行
page        = block_tables[req, c // 16]
table[t, j] = page × 16 + c % 16                       # 第 j 个候选的物理 tile

kept        = 有效候选数（非 −1）
last_span   = min(max(visible − last × 8, 0), 8)       # 最后一个候选块里真正可见的行数
context[t]  = (kept − 1) × 8 + last_span              # candidate_table.py:71–72

为什么一个长度就够

候选块按升序排列，除了最新的那一块都是满的 8 行，而最新块被第 20 层强制选中（块分数置 +inf），所以它一定排在最后。 于是紧凑宽度里的前 context 列恰好全是有效行，不需要逐列的掩码。万一最新块丢了，last_span 被夹到 8，最多读满一块，不会越界。

第 2 步 · 打分

同一个公式，只是列数从 L 变成至多 16,384

score_topk_quantized 发现传进来的是 candidates，就把 table 当块表、context 当每行的上界、 width = 2048 × 8（atom/model_ops/deepseek_v41/paged_scoring.py:102）。之后与第 20 层完全一样： 

logit[t, c] = Σ_h  scaled₂₄[t, h] · ReLU( iq₂₄[t, h] · K₂₀[该列对应的行] ) · k_scale
              c ∈ [0, context[t])                # 第 24 层的 query，第 20 层的 key
→ top_k_per_row_decode(k = 512, stable = True)  # 压缩宽度里的列号，升序，不足补 −1
  • FP8 index plane 的 tile 就是 8 行（后端把 index_block_rows 设成 candidate_block_size），所以候选块号可以直接当块表用；代码里有 assert 核对 candidates.rows_per_block == tile。
  • REINDEX 不产出候选：atom/model_ops/deepseek_v41/paged_scoring.py:133 断言 candidate_count 与 candidates 不能同时给。
  • FP4 index plane 下，REINDEX 不走「整请求 ragged」那条路（_ragged 只给没有候选来源的 FULL 层），每行照样用自己的候选表。

第 3 步 · 换算

压缩列号 → 候选槽 → 逻辑块 → token 位置，顺序不变

例子

decode 到第 100,000 个位置时，第 24 层怎么选

例子 · decode，t = 100,000

  1. 第 20 层：visible = 100,001 行，共 12,501 块。最后一块是第 12,500 块，里面只有第 100,000 行这一行，块分数置 +inf。 candidates[20] 是 2048 个升序块号，最后一个一定是 12,500。
  2. 翻译：例如候选块 c = 37 → 页列 37 // 16 = 2 → 查块表得物理页 p → tile = p × 16 + 5。 context = 2047 × 8 + min(100,001 − 12,500 × 8, 8) = 16,376 + 1 = 16,377。
  3. 打分：第 24 层的 32 头 query 对这 16,377 列打分，每列 8,192 FLOP，约 134 MFLOP，取 top-512。
  4. 换算：例如压缩列 16,376 → 槽 16,376 // 8 = 2047、块内 0 → 块 12,500 → 行 12,500 × 8 = 100,000，也就是当前 token 自己。
  5. 第 28 层：直接复用第 2 步的表（step.candidate_blocks[20] 已经有了），只用自己的 query 再打一遍。

边界与成本

上下文不到 16,384 时它就是全量重打；超过之后成本封顶

成本

常数

每行最多 16,384 列 × 8,192 FLOP ≈ 134 MFLOP，加上 wq_b 与 weights_proj 约 11 MFLOP（四卡合计，估算），与上下文长度无关。

对比

第 20 层线性增长

同样在 t = 100,000，第 20 层要打 100,001 列，约 819 MFLOP；四个 REINDEX 层加起来约 537 MFLOP。

换来的

decoder 不同深度看不同的历史

同一份 main_20，被选了 5 次：第 20 层一次全量，第 24/28/32/36 层各一次候选内重选，每次用的 query 更深一层。

读码路线

从 _bounds 到 lift

  1. atom/models/deepseek_v41/config.py:137：REINDEX 的判定；candidate_owner 在同一个循环里填。
  2. atom/models/deepseek_v41/attention.py:122 Indexer.score → atom/models/deepseek_v41/attention.py:204 _bounds：candidates 与 candidate_count 二选一。
  3. atom/model_ops/attentions/deepseek_v41/cache.py:674 candidate_blocks → atom/model_ops/deepseek_v41/candidate_table.py:160 bind_candidates → atom/model_ops/deepseek_v41/candidate_table.py:111 candidate_block_table。
  4. atom/model_ops/deepseek_v41/paged_scoring.py:102 score_topk_quantized：候选分支设 table / bound / width，第 182 行调 lift。
  5. atom/model_ops/deepseek_v41/candidate_table.py:172 lift_candidate_selection；两个 kernel 各有一个纯 torch 的 *_reference 版本，逐 token 循环写，读起来最直白。

读码坑

候选块号、index tile、PAGE 内的块编号是三套东西，只有在「candidate_block_size == index tile 行数」时才能互相当块表用； 这个相等是后端显式声明的（index_block_rows = candidate_block_size，atom/model_ops/attentions/deepseek_v41/backend.py:164），不是推出来的，改 V4.1 的候选块大小必须同时改 index plane 的分块。
