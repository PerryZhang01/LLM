Full 层：encoder 段里生产记忆的三层

第 2、8、14 层各自把本层的 attention 输入每 2 个 token 压成一行，写成一份全局 KV，再顺手为每一行生成一个 128 维的 index key； 然后用自己的 index query 对整段历史打分，选出 512 行。同段后面 5 层这三样都直接借用，只算自己的窗口。 这一章从 Compressor 的逐维 softmax 讲到 top-512 怎么变成池里的物理行号，每一步标 shape，关键处配算得出数的例子。

定位

encoder 每 6 层换一份新记忆，由段首的 FULL 层生产

topology 里 kv_source_layer_ids 的前三项是 2、8、14（atom/models/deepseek_v41/config.py:75）。每个 owner 的 kv_owner 和 topk_owner 都是它自己，后面 5 层的这两个字段指回它，所以一段 6 层共用同一份全局 KV、同一份 index key、同一次 top-512 选择。 越往后的段，压缩的是越深的表示。第 14 层还是 Engram 层：attention 接缝之前先把 n-gram 记忆写进残差，Compressor 读到的已经是注入记忆之后的输入。

D 步 · Compressor

两个 token 逐维 softmax 加权，合成一行 512 维 latent

Compressor 只读本层的 attention 输入 h，是一层里最早能开始的工作，所以 forward 第一件事就是把它发到 compress stream 上 （atom/models/deepseek_v41/attention.py:357）。它分三段：投影、池化、两路写出。

  1. 投影。wkv_gate 是 [wkv; wgate] 融合成的一个 GEMM，5120 → 2 × 512，BF16 权重，输出要求 FP32（otype=torch.float32，atom/model_ops/deepseek_v41/compressor.py:136）。 源码注释说这个参数是承重的：官方模型规定池化在 FP32 里做，GEMM 先舍入到 BF16 就偏了。输出拆成 values [T, 512] 与 scores [T, 512]，零拷贝的两半。
  2. 分组。compress plan 里只有位置满足 (pos + 1) % 2 == 0 的 token，也就是每组的第二个 token 触发压缩；第 s 组覆盖 token 2s、2s+1。
  3. 池化。512 维每一维各自在组内两个 token 上做 softmax，用得到的权重对 values 加权求和，然后 compressor.norm 做 RMSNorm，得到 latent。
  4. 写全局 KV。latent 的后 64 维在组起点位置 2s 做 RoPE（global_rope），写进 main_2 的第 s 行。FP8 池的行是值和 scale 交错的 MXFP8，融合 kernel 写不了，所以这时它只回传旋转后的值，cache.compress 再量化、scatter（atom/model_ops/attentions/deepseek_v41/cache.py:574）。
  5. 写 index key。RoPE 之前的 latent 交给 Indexer.write_keys：wk [512 → 128] → k_norm → 同样在 2s 处 RoPE → 量化，写进 index plane[2] 的第 s 行（atom/models/deepseek_v41/attention.py:79）。index key 的旋转位置必须和主行一致，否则选出来的是别的行。
  6. 尾巴。本 forward 末尾凑不满一组的那个 token，它的 values / scores 以 FP32 留在 STATE（compress_state(owner)，atom/model_ops/attentions/deepseek_v41/cache.py:711），等下一个 token 来了再一起池化。尾巴不进 checkpoint：checkpoint 只落在 PAGE 边界，128 是 2 的倍数，边界上没有半组。

两份存储

每个压缩行存两样：给 attention 的 512 维，给打分的 128 维

Indexer 打分要把可见历史整段扫一遍，如果直接读 512 维的 KV，长上下文下带宽吃不消。所以每一行再存一份 128 维、低精度的 index key， 先用它把历史粗筛出 512 行，attention 只读这 512 行的完整 KV。可以把 main_2 看成书的正文，index plane 看成目录卡片。

生产

只有 owner 写

每个组凑满时写一次，之后不再改动。REUSE 层没有 wk、k_norm，也就没有自己的 index key。

消费

只给打分用

attention 从不读 index key。第 2/8/14 层的 index key 只被各自的 Indexer 读；第 20 层的还被第 24/28/32/36 层读。

格式

FP8 默认，FP4 可选

index_cache_dtype 与主池格式无关。FP4 是官方算术（E2M1，每 32 维一个 E8M0），由一个 aiter kernel 同时做 norm、RoPE、量化、写入。

E 步 · Indexer 打分

32 个头各自和同一个 key 做内积，过 ReLU，再按 token 自己的权重加起来

打分的三样输入里，index key 来自 plane，另外两样由当前 token 现算（Indexer.project，atom/models/deepseek_v41/attention.py:99）：

iq_t [32, 128]
indexer.wq_b(qr_t)，在位置 t 做 RoPE。qr 是本层主 query 路径上 q_norm 的输出，两边共用，而且直接复用它的 MXFP8 版本，不再量化一次。
w_t [32]
weights_proj(h_t)：每个 token 自己决定 32 个头各占多少比重。
K_s [128]
index plane 第 s 行。

为什么一定要有 ReLU

没有 ReLU 时，Σ_h w[h]·(iq[h]·K) = (Σ_h w[h]·iq[h])·K：32 个头先合成一个 128 维 query，再和 K 做一次内积，多头就退化成单头。 有了 ReLU，每个头成了一个独立的检测器，只在 key 落在它关心的方向上时给分，否则输出 0。一行的分数大致等于「有多少检测器被触发、触发得多强、当前 token 有多看重它们」。

因果与边界

每个 query 行只看自己请求里、已经凑满的压缩行

batch 里混着多个请求的 prefill 行和 decode 行。打分器把每一行当成一个独立单元（next_n = 1），每行带自己的可见上限， 并且只按自己请求的 PAGE 表读 index plane（tile 列表由 atom/model_ops/attentions/deepseek_v41/cache.py:643 的 unit_tiles 展开）。 可见上限在 host 侧一次算好：visible = (pos + 1) // ratio（atom/model_ops/attentions/deepseek_v41/metadata.py:296）。

例子 · 同一个 batch 的三个请求

A：prefill 位置 0–9。本 forward 的 D 写出第 0 行（token 0,1）到第 4 行（token 8,9）。各位置的 visible 依次是 0,1,1,2,2,3,3,4,4,5。

B：decode 位置 1000。visible = 1001 // 2 = 500，不足 512：500 行全部入选，后面补 12 个 −1。

C：decode 位置 5000。visible = 2500，打 2500 个分，选出 512 行。

所以 ratio 2 的层要到上下文超过 1024 个 token，top-k 才真正在筛选；在那之前它等于把可见行全选上。

E 为什么要等 D

visible 已经把「本 forward 刚跨过的组边界」算进去了，所以第一个读这一行的就是本层的打分。_select 在打分前等 compress stream （atom/models/deepseek_v41/attention.py:393）。两条旁路是否真的分到别的 stream，由 ATOM_DSV41_SIDE_STREAMS（0/1/2）决定；不分时这条等待就是同一 stream 上的先后顺序。

取 top-k 与生成下标

按行取 512 个升序列号，再由下标组首层一次换成 6 层的物理行

调用链是 Indexer.score（atom/models/deepseek_v41/attention.py:122）→ score_topk_paged（atom/model_ops/deepseek_v41/paged_scoring.py:63） → score_topk_quantized（atom/model_ops/deepseek_v41/paged_scoring.py:102）→ 共享打分器 score_topk / _score_paged （atom/model_ops/indexer/score.py:50、atom/model_ops/indexer/score.py:144）。行被切成若干 band，每个 band 的 logits 写进常驻工作区， 不超过显存预算（ATOM_SPARSE_INDEXER_LOGITS_BUDGET_MB，默认 2048 MiB），也不超过 int32 的寻址范围。

下标是按下标组生成的：(ratio, kv_owner, topk_owner) 相同的一段连续层，由组首层在第一次被问到时一次生成， 后面的层查到现成的结果直接取用，不再启动 kernel（attention_indices，atom/model_ops/attentions/deepseek_v41/cache.py:911）。 组首层恰好就是做选择的那一层，所以轮到它问的时候，组里共享的输入都已经算好了。

成本 · 按形状估算

FULL 层贵在打分：每个 token 都要把 L/2 行扫一遍

项目每个 token、每个 FULL 层说明
打分乘加L/2 × 32 × 128上下文 100 万时约 2.0 G 次乘加（4.1 GFLOP）；第 2/8/14 三层合计约 12 GFLOP
扫描字节L/2 × 132 BFP8 index plane；FP4 约一半

index key GEMM512 × 128只对凑满的组，即每 2 个 token 一次
attention≤ 512 + 128 个 key和 REUSE 层一样，与 L 无关

prefill 时 encoder 不参与 bounded replay：三个 owner 的 Indexer 要在全部 prompt 行上打分，量级是 L × L/2。 开启 decoder replay 后，长 prompt prefill 的打分开销主要就落在这三层（第 7、10 章）。

读码路线

按 D → E → F 的顺序读，每一步都有一个能单独测的函数

  1. Attention.forward 先看分叉顺序：_fork_compress → project_qkv → qk_norm → _fork_select（atom/models/deepseek_v41/attention.py:357、atom/models/deepseek_v41/attention.py:393）。
  2. Attention._compress_batch（atom/models/deepseek_v41/attention.py:299）→ cache.compress（atom/model_ops/attentions/deepseek_v41/cache.py:574）→ compress_batch（atom/model_ops/deepseek_v41/compressor.py:21）。
  3. Compressor.project 与它的参考实现 pool（atom/model_ops/deepseek_v41/compressor.py:125、atom/model_ops/deepseek_v41/compressor.py:138）：pool 是 torch 写的同一套数学，读它最快。
  4. Indexer.write_keys → cache.write_index（atom/models/deepseek_v41/attention.py:79、atom/model_ops/attentions/deepseek_v41/cache.py:599）。
  5. Indexer.project / score → score_topk_paged → score_topk / _score_paged（atom/model_ops/deepseek_v41/paged_scoring.py:63、atom/model_ops/indexer/score.py:144）。
  6. cache.attention_indices → _index_group → build_indices（atom/model_ops/attentions/deepseek_v41/cache.py:911、atom/model_ops/attentions/deepseek_v41/cache.py:947、atom/model_ops/attentions/deepseek_v41/indices.py:370）。

读码坑

「没有压缩计划」不等于出错

_compress_batch 在 step.plans 为空时直接返回：那是 bounded replay 的 tail step（压缩已在全部行上做过），或空闲 DP rank 的哑 prefill。

读码坑

top-k 的宽度是预留好的

每行的选择数不是数出来的，而是按 min(visible, 512) 的闭式算的；打分器的输出宽度必须正好是 512，build_indices 对不上就直接报错。
