Window 层

第 0、1 层的 attention 只看最近 128 个 token，没有全局 KV，也不打分——是 CSA2 八步里最短的一条路径。 但「窗口」本身不是这两层独有的：40 层每层都在请求的 STATE 里有一段 128 行的 ring，其余 38 层只是在它之外再加一路选中的全局行。 所以这一章既讲 WINDOW 模式，也把所有层共用的 ring 讲透：它存在哪、地址怎么算、prefill 和 decode 什么时候读写。

定义

WINDOW 是一种模式，窗口 ring 是每一层都有的存储

拓扑表里 ratio 为 0 的主干层被标成 AttentionMode.WINDOW（atom/models/deepseek_v41/config.py:114），Flash 上只有第 0、1 层。 这两层不生产、也不读任何全局 KV，attention 的 key 只有窗口那一路。

WINDOW 模式

第 0、1 层

只有窗口这一路。D（Compressor）和 E（Indexer）都不存在，F 生成的下标里只有窗口行。

每层都有的窗口

40 层 × 1 段 ring

第 2–39 层的 attention 同样有窗口这一路，ring 结构、地址公式、读写时序与 WINDOW 层完全相同；它们只是多了源 1。

草稿层

第 40–42 层

DSpark 的 3 层也是 ratio 0，也有自己的 ring，但 KV 来自目标模型第 37–39 层，块内双向可见。放在本章最后单独讲。

前向

八步里跳过压缩和打分，剩下的六步与其他层逐字相同

D 被跳过不是靠判断层类型，而是 _compress_batch 的第一个条件 not self.spec.ratio 直接返回（atom/models/deepseek_v41/attention.py:299）； E 被跳过是因为构造时就没有 Indexer（atom/models/deepseek_v41/attention.py:290 起只给 FULL / REINDEX 建）。

第 0 层的特殊处

接缝不补写，pre 是 one-hot

它前面没有子层，接缝的 ① 无事可做；带进来的 pre_mix = [1, 0, 0, 0] 把 4 份相同的残差合成 embedding 本身。见 第 2 章。

第 1 层的特殊处

attention 之前有 Engram

接缝先 settle（把第 0 层 FFN 的 post 写回），再做 Engram，再做接缝的 ②③④。所以第 1 层的窗口 KV 来自已经注入 n-gram 记忆的残差。见 第 3 章。

存储

ring 在请求的 STATE 条目里，按 pos 对槽数取模

每个在途请求占一个 STATE 槽。槽里依次是 40 层的窗口 ring、compressor 的 FP32 尾巴、以及 cursor（位置 + 最近 3 个压缩 id）， 由 atom/model_ops/attentions/pool_layout/v41_pool_geometry.py:334 的 state_fields 声明。第 L 层的 ring 从 ring_start(L) 开始，绝对位置 pos 落在第 pos % ring_slots 个槽。

例子 · 为什么要多留投机槽

开 DSpark 5 时，一轮验证一次写入最多 6 行（1 个输入 + 5 个草稿）。如果 ring 只有 128 槽，被拒绝的草稿行会覆盖下一轮窗口还要读的旧行。 多出的 5 槽保证：本轮被丢弃的写入，最远只落到下一轮提交位置之后 5 个槽，在下一轮读取的 128 行之外。代价是每层每请求多 5 × 528 B。

时序

decode 先写后读，prefill 先读后写

位置 t 的窗口是 [max(0, t − 127), t]，包括自己（atom/model_ops/attentions/deepseek_v41/indices.py:73 的 first = max(pos − WINDOW + 1, 0)）。 这 128 行在 decode 和 prefill 里来自不同的地方：

C 步（rope_quant_window）G 步读窗口何时写 ring
decode旋转、量化，并把本行直接写进 pos % ring_slots源 2 = ring_view(layer)（atom/model_ops/attentions/deepseek_v41/cache.py:942），已含自己C 步
prefill只产出 KV 行，不写prefix 里放 ring 中 chunk 起点之前的行；源 2 = 本 forward 的 extendH 步之后，write_window

位置编码

窗口层用 θ = 10000、不带 YaRN 的那张表

atom/models/deepseek_v41/model.py:381 按 ratio 选表：ratio 为 0 的层用 window_rope（atom/models/deepseek_v41/model.py:297，base = rope_theta = 10000）， 其余 38 层用 θ = 160000、YaRN ×16 的 global_rope。DSpark 草稿模型自己的 self.rope 也是 base = rope_theta。

推断

窗口层里 query 和 key 的距离永远不超过 127，RoPE 只需要在这么短的相对距离上分辨位置，不存在长距离外推的问题，所以不需要为 100 万上下文做的频率缩放。 全局层要和整段历史里的压缩行做相对位置，才需要 YaRN。代码里只写了「用哪张表」，没有写理由。

与 bounded replay

重算的 forward 里，窗口下界可能被截断，也可能读旧 ring

window 层属于 encoder（第 0–19 层），两种 bounded replay 都会碰到它的窗口。两个控制量都在 step 元数据里（atom/model_ops/attentions/deepseek_v41/metadata.py:143）： swa_replay_start（窗口最低能读到哪）与 swa_cached_until（ring 里哪个位置以下的行是现成且精确的）。

草稿层

第 40–42 层也是窗口层，但 KV 从目标模型借，块内双向

DSpark 的 3 个草稿层是 DraftAttention（atom/models/deepseek_v41/dspark.py:45）。它们的上下文 KV 不是自己的输入投影出来的，而是目标模型第 37–39 层的输入拼起来、经 main_proj 降回 5120 维后再投影； 可见列表由 atom/model_ops/deepseek_v41/draft_block.py:21 的 draft_step 给出。

设计

为什么最底下两层只看窗口

代码和文档都没有给出理由。V4 的配置同样是第 0、1 层（以及最后一层）为纯窗口，可见这是沿用下来的设计。下面是推断：

  • 最底层的表示接近原始词嵌入，主要在做局部的拼词、组词。把它压成全局 KV 去做长程检索，收益有限。
  • 先用两层局部 attention、再加第 1 层的 Engram 把局部词法信息整理好，第 2 层生产的第一份全局 KV 压缩进去的就是更有用的表示。
  • 纯窗口层不随上下文增长：100 万上下文时，这两层每个 token 仍只看 128 个 key，没有打分开销。

读码路线

从拓扑表到 ring 的一个字节

  1. atom/models/deepseek_v41/config.py:114：ratio 0 怎样变成 WINDOW。
  2. atom/models/deepseek_v41/attention.py:299 _compress_batch 的第一个 if，以及 atom/models/deepseek_v41/attention.py:447 _attend 里 decode 与 prefill 两个分支各在哪写窗口。
  3. atom/model_ops/attentions/deepseek_v41/cache.py:787 rope_quant_window 的 docstring：为什么 decode 能把写入并进这一次 launch，prefill 不能。
  4. atom/model_ops/attentions/deepseek_v41/indices.py:25 _indptr_scan：窗口的 history / reach 两段怎么算。
  5. atom/model_ops/v4_kernels/pool_index.py:63 window_row 与 atom/model_ops/attentions/pool_layout/v41_pool_geometry.py:395 window()：一行在池里的地址。

读码坑

window_row 用的是 Triton 的取余语义，负数 pos 会得到负的行号而不是回绕；调用方必须先把 -1 的 padding 哨兵挡掉（pool_index.py 的 docstring 写明了这一点）。 另外「窗口 128」在开投机时并不等于「ring 128 槽」：读取宽度仍是 128，槽数是 128 + 投机 token 数。
