投机解码与采样

DeepInfer 的投机解码有两个特点。一是草稿一次 forward 出整块，不是逐个自回归。 二是每个草稿 token 都带一个「会被接受的概率」，调度器据此决定这一步验证多少个。 验证用真正的拒绝采样，输出分布不变。采样器从随机数到求和顺序都和批的组成无关，所以确定性采样可以只靠开关打开。

关键 feature · DSpark

草稿是块并行的：一次 forward，B 个位置

代码里 DSpark 的实现叫 DFlash（models/mtp/dflash.py）。草稿输入是一块 B 个 token： 第 0 位放目标模型刚采到的 token（golden），其余位置放一个专用的 noise token（_embed_draft_init_tokens）。 B 就是 DEEPINFER_USE_NEXTN_DECODE，默认 5，设 0 关闭投机解码。 草稿层对这一块做一次非 causal 的 forward，所以 B 个位置的 logits 同时出来。 唯一串行的部分是一个很便宜的一阶 Markov 修正。

草稿看到什么

  • 主模型 dspark_target_layer_ids 那几层的 attention 输入，在 mHC 的 4 路上取均值后拼接，经 projection → projection_norm → main_kv_proj 变成每个草稿层一条 MQA key，写进该草稿层的 SWA 缓存
  • 这一步在主模型 forward 里完成（update_main_cache），所以在主 CUDA 图内。prefill 时只跑这一路，不做草稿 prefill
  • 同一请求的 B 个草稿槽共用一行 kv_index：窗口 [accepted_pos − W + 1, accepted_pos + B]，attention 以 causal=False 调用

草稿状态只活一步

  • 草稿 key 只在本步有效，下一步覆盖（attn.py:975-991）
  • 被拒位置的主缓存 key 不清除：下一步的写入恰好落在同一批槽上，读之前已覆盖
  • MTPInfoPool 有 (max_num_seqs + 1) × nextn 行；0 号槽是填充，内容是 token vocab_size − 1 上的 one-hot。prefill 之后的第一次 decode 验证的就是这些填充草稿
  • 草稿采样用的是请求自己的温度、top-p、top-k，这样草稿分布 q 与目标分布 p 处在同一组采样参数下

关键 feature · 置信度调度验证

验证多少个草稿，按「期望接受数 ÷ 实测耗时」算

固定验证 5 个是浪费：接受概率随请求、随位置都不同，排在后面的草稿多半会被拒。 打开 DEEPINFER_ENABLE_MTP_VARLEN=1（默认关；eval/run_eval.py 打开）后，MTPVarlen::schedule（mtp_varlen.hpp:150-267）每步这样做：

  1. 每个草稿位置的期望接受率取置信度的累乘。源码注释：「modeling 返回的 confidence rate 是每个 token 独立的，使用前要做一个累乘」（scheduler.hpp:1248）。
  2. 全批所有 (累乘率, 序列下标) 放进一个列表，降序排序，同分按下标。
  3. 从 num_seqs 个必算行（每条的 golden 位，期望产出 1）开始，按顺序逐个加草稿。每个候选总量的耗时估为 baseline(装得下的最小图) + slope × graph_size + sampler_ms，取「期望 token ÷ 耗时」最大的那个总量。
  4. 每条请求分到 1 + 它落在前 (best_total − num_seqs) 名里的草稿数。

耗时模型是在线拟合的

baseline 来自 warm-up 时实测的每张 decode 图耗时（第 2 章）。 slope 用来补上下文长度的影响：对最近 5000 步的 (forward_ms − baseline) / graph_size 取中位数的中位数，只用样本 ≥ 10 的档位，并截到 ≥ 0。 sampler_ms 按 num_seqs 分组，取最近 9 个的中位数。数据来自图内的 CUDA 事件，经 update_mtp_runtime 回灌。

两轮滞后与无损性

总预算用 N−2 轮的置信度，按请求分配用 N−1 轮（schedule_cnt / process_cnt 区分）。注释写的不变量是： 「confidencei+1..nextn 不能影响 drafti 是否被验证」。 推断：置信度 i+1 经 Markov 嵌入依赖草稿 i 的取值。如果它能决定 i 验不验，验证的选择就和草稿内容相关，拒绝采样的无偏性会被破坏。累乘率在请求内单调不增，同分按下标，所以全局 top-k 在每条请求内总是一个前缀。

ZOS 下 CPU 拿不到第 N 轮的置信度，于是 CPU 只定 total_q。GPU 内核 compute_seqlens_q_by_confidence_rates 用 remap 取上一步的原始置信度（新序列取 0），做累乘，再给每个 (seq, pos) 算排名（多少个条目比它高，或同分且下标更小）， seqlen_q = 1 + #{rank < total_q − num_seqs}。结果拷回 pinned 缓冲，采样前 CPU 用它修正元数据。

关键 feature · 无损验证

验证是真拒绝采样，并给出了误差界

验证行 j 的 logits 用来判第 j 个草稿，最后一行做一次新的采样（bonus）。判定融合在 fused_sample_tl 里： 若 U < exp(min(log p(d) − log q(d), 0)) 则接受，否则从残差 max(p − α·q, 0) 里重采，残差全为 0 时退到 argmax。 α = exp(−DRAFT_PROB_PENALTY)，DRAFT_PROB_PENALTY = 5e-5，注释说是为了「防止 reject sampling 采不出东西」。 tilelang_ops/common.py:3-19 给出了由此带来的分布误差上下界：q[j] − ε/(1+ε) ≤ A[j] ≤ (1+ε)·q[j]，其中 ε = 1 − e−penalty。

温度 0 没有特例

SamplingParams 把小于 1e-5 的温度夹到 1e-5，并关掉 top-p / top-k（sampling_params.py:76-79）。greedy 走的是同一条采样路径。

前缀接受

get_accept_result 把逐行判定变成「接受到第一个被拒为止」，并处理 golden token 覆盖（teacher forcing）。finalize_verification 写出每步接受数与验证数。

置信头的校准量

每步算 Σ|accept_prob − confidence|，其中 accept_prob = 1 − 残差质量。它出现在统计日志里，可以直接看出置信头有没有校准好。

采样器

一个融合内核，求和顺序与批无关

整批采样是一个 TileLang 内核 fused_sample_tl，分两次发射，用 PDL 串起来。 第一次做逐行在线 log-sum-exp，归约布局固定，注释说是「为了和参考交叉熵实现逐位对齐」。 第二次做三件事：在保序 uint32 键上用 radix select 找 top-p / top-k 阈值；写出 logprob；做新采样，或做上一节的验证与残差重采。 阈值搜索时，概率质量按定点 uint32（scale 231）整数原子加累计，所以原子加的先后顺序不影响结果。阈值处的平票按列下标切开。

支持不支持
temperature、top-p、top-k；top_logprobs（≤ 1000）、prompt logprobs；first_n_token_no_eos；golden_token_ids（teacher forcing）；全局 token 黑名单 DEEPINFER_DECODE_TOKEN_BLACKLIST；强制 top-k 预筛 DEEPINFER_SAMPLER_FORCE_TOPK（默认 0，示例用 4096，DeepSelect 先缩小 logits，草稿分布 remap 到同一 top-k 空间） min-p（Sampler docstring 提到，但 SamplingParams 没有这个字段）；repetition / presence / frequency penalty；停止字符串；n > 1；beam search

随机数按「位置」生成，不按「批里第几行」

关键 feature · 批不变推理

一个开关，覆盖 GEMM、MoE、mHC 和 FlashMLA

DEEPINFER_BATCH_INVARIANT=1 的目标是：同一条请求，不管和谁拼在一个批里，结果逐位相同。它在代码里只出现在四处：

位置效果
worker/runtime_config.py:67-69进程级打开 deep_gemm.use_deterministic_algorithms(True) 与 tile_kernels.use_deterministic_algorithms(True)：稠密 GEMM、logits GEMM、分组 GEMM 与 mega MoE、MoE gate 与量化、mHC 内核都受影响
v4_modules/attn.py:666, 1002decode 的稀疏 / 滑窗 attention 和 DFlash 草稿 attention 调 flash_mla_with_kvcache(..., enable_batch_invariant=True)
v4_modules/attn.py:89稠密 packed-KV 层（无 top-k）平时只在 PROMPT 引擎里用融合的 norm + RoPE + attn + cast 内核；开批不变后这里也退回非融合路径。V4.1 的压缩层都带 top-k，推断实际碰不到这条
parallel_utils/userbuffer.py:79EPLB 重排打开时，DeepEP 设 allow_multiple_reduction=False

确定性采样的三个条件

  1. DEEPINFER_BATCH_INVARIANT=1
  2. DEEPINFER_ENABLE_MTP_VARLEN=0：变长验证时每条的验证长度来自全批排序和墙钟耗时估计，验证行的随机数键（local_step）跟着变
  3. 给 SamplingParams 传固定的 seq_seed

只支持 NVIDIA：NPU 上 runtime_config.py:61-63 直接断言关闭（「待完整支持 batch invariant 后移除」）。NPU 反而总是打开 DeepGEMM / TileKernels 的确定性模式，注释是「防止 CI 数值不稳定」。

怎么测

tests/models/test_batch_invariant.py：64 条序列以 nextn=5 批量生成，再把每条单独重放， 并用 golden_token_ids 喂入批量的输出，要求 token、logprob、top-logprob 全部相同。 test_sampler.py 则用随机化 PIT + KS 检验验证采样分布本身是对的。 代价没有给数字，eval/run_eval.py 的帮助文本只写了「slower」。

关键 feature · 结构化输出

xgrammar 编译放到后台，掩码与投机解码兼容

编译

  • 用 xgrammar：so_args = {"schema_type": "json" | "regex" | "ebnf", "schema": ...}，JSON 用 strict 模式
  • 在绑核的线程池里异步编译（DEEPINFER_SO_BUILDER_CPUS=4），超时 20 秒，缓存上限 10 GiB
  • 扩展：trigger_token_ids 让语法在某个 token 序列出现后才生效（KMP 匹配），bound_token_id 强制把触发序列补完
  • 部署文档里，编译在单独的 SO 机器上做，请求进引擎前取编译结果

掩码与投机解码

  • 掩码不融合进采样器：CP rank 0 在 CPU 上建每步 bitmask，在侧流上拷到 GPU，与 logits GEMM 重叠；再由 apply_token_bitmask_by_step_inplace 把非法 token 置 −inf
  • matcher 先吃进已提交的 token，填掩码 0；再试探性地吃草稿 k、填掩码 k+1，遇到语法拒绝的草稿就停，最后回滚（max_rollback_tokens = nextn + 2）
  • 草稿本身不受约束地采。非法草稿在目标分布下概率为 0，拒绝采样会自动拒掉它
  • 带 SO 的请求被抢占时无法重算，直接 FINISHED_PREEMPTED；matcher 出错只杀本请求（FINISHED_SO_FAILED）
