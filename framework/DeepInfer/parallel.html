第 5 章 Attention DP Wide-EP 镜像 CP EPLB NVIDIA / Ascend

并行与算子层

DeepInfer 只用三种并行：attention 和稠密层走 DP，路由专家走 EP，长 prompt 的 prefill 可选 CP。 没有 TP。MoE 在 NVLink 域内是一个融合到底的 mega 内核，跨域才走 DeepEP。 跨平台靠一个 30 行的分发文件：同一套 Python 接口，后端在 cuda/ 和 asc/ 之间切。

进程组

没有 TP，DP 数缺省等于 EP 数

ParallelConfig 里 data_parallel_size 缺省取 ep // cp，model_parallel_size = cp， world = max(dp × cp, engram_parallel)（config.py:150-182）。 所有稠密投影都是 ReplicatedLinear，embedding 与 lm_head 也是整份复制；只有路由专家按 EP 切，Engram 表按 Engram 并行组切行。

组成员用途
dp各引擎里 cp_rank 相同的 rank投票决定步型；另有 gloo CPU 孪生组
cp连续 cp_size 个 rank镜像 CP 的 all-gather、调度结果广播；另有 gloo 孪生组和 shm 消息队列
ep连续 ep_size 个 rank（ep = world 时就是全体）MoE dispatch / combine、EPLB 统计与搬运
enpEngram 并行组Engram 表按行分片，经 DeepEP EngramBuffer 读
ep_in_dp—EP 内的辅助组（另有 gloo 版）

NCCL 通信器按需惰性创建，init_device_groups() 用一次 dummy all-reduce 强制建好。worker 启动时设 NCCL_CUMEM_ENABLE=1、NCCL_PXN_DISABLE=1（注释：为专家重排），删掉 NCCL_NVLS_ENABLE，NCCL 的 CTA 数钉在 32（DEEPINFER_NCCL_NUM_SMS）。

部署文档里的形状并行取值原则
PrefillEP2–8 / DP2–8显存允许的最小值，跑在普通 8 卡机上
DecodeEP64–128 / DP64–128卡允许的最大值（Wide-EP）：降低每步 MoE 的访存量，配合 EPLB 提高 TPS
VE（视觉编码）单卡 / 实例推荐用便宜的卡
TP · CP不用「暂不使用」

P 与 D 的卡数比实践中约 1:1。decode 推荐 EP64 以上，所以最小的高效部署单元是 64 卡 prefill + 64 卡 decode。

关键 feature · 镜像 CP

只给 prefill 用的 zigzag 切分

每条序列切成 2·cp 段，每段 ps = ⌈sq / 2cp⌉ 个 token。rank r 拿第 r 段和第 2cp−1−r 段， 参考实现 prepare_cp_mirror_ref 的 docstring 写的就是「directly expands the zigzag definition」。 调度器把分块长度对齐到 2·cp，正是为了这个切法。

关键 feature · MoE

NVLink 域内一个 mega 内核，跨域走 DeepEP

路由打分是 sqrtsoftplus，top-k 方法 noaux_tc 带 e_score_correction_bias，图像 token 另有一份 bias_vl。 GPU 上 gate 是融合的 deep_gemm.bf16_mega_gate，EPLB 的逻辑到物理专家映射和专家计数都在里面。 格式固定：激活 FP8 e4m3，每 32 个一个 ue8m0 scale；路由专家权重 MXFP4（mma_type = fp8xfp4）；shared expert 是一个 FP8 MLP。

DeepEP 路径的细节

  • 一个 EPBuffer，按 is_prompt 切换每 rank 最大 token 数，代码里没有分 normal / low-latency 两种模式
  • 标志：allow_hybrid_mode、do_expand、async_with_compute_stream、defer_epilogue
  • do_cpu_sync 只在 prefill 用，YOCO compact 模式下也关掉
  • 通信 SM 数 DEEPINFER_USERBUFFER_COMM_SMS 默认 0 = 自动：min(理论值, SM 数 − min(32, SM 数 / 4))

userbuffer 是什么

_UserBufferManager 是进程级的通信缓冲持有者：DeepEP 的 EPBuffer（MoE）、BucketBuffer（CP all-gather）、 EngramBuffer（RDMA 上的 Engram 表），以及 DeepGEMM 的 SymmBuffer（第一个规格必须最大，后面的都是它的视图）。 它不是 all-reduce 或 NVLS 机制。nccl_memory.py 只是每 1000 步打一次各通信器的显存占用。

关键 feature · EPLB

冗余专家、滑窗统计、在 NVLink 内直接拉权重

冗余槽

DEEPINFER_OVERRIDE_NUM_EXTRA_EXPERTS 是下限，引擎把 routed + extra 向上取整到 ep_size 的倍数。初始布局是 [0..n−1, i % n]，权重加载器按同一映射只读本 rank 的专家。

策略

先 EP 内 all-reduce 逻辑专家计数，然后在 GPU 上做两步贪心：把每个冗余槽给「使窗口内各步最大副本负载之和最小」的逻辑专家；再按负载降序放置副本，每个副本放到「使各步最大 rank 负载之和最小」的 rank 上，受每 rank 容量约束。同布局的 MoE 层共用一个均衡器，所以主模型和 DFlash 的 MoE 分开均衡。

搬运

NVLink 域内（仅 GPU）：每层一块 torch symm_mem 镜像缓冲，barrier → 把自己的权重拷进镜像 → barrier → 直接从对端镜像拉缺的专家。域外：NCCL batch_isend_irecv。两种都在采样阶段同步执行，在 CUDA 图之外。

关键 feature · 双平台

后端选择只发生在一个文件里

deep_cluster.hardware.accelerator_kind() 看设备节点：有 /dev/davinci_manager 就是 Ascend，有 NVIDIA 设备节点就是 NVIDIA。 deepinfer.PLATFORM 惰性创建，决定通信后端、TileLang 后端和一堆小差异。 所有 TileLang 内核都经过 ops.py 取得： 

# deepinfer/model_executor/layers/tilelang_ops/ops.py（全文 32 行，节选）
"""Kernel dispatcher: interface modules do ``from ... import ops`` and call
``ops.xxx_tl``; backend selection happens only in this file."""
_pkg = importlib.import_module(f"{__package__}.{PLATFORM.tilelang_ops_backend}")   # "cuda" | "asc"
for _info in pkgutil.iter_modules(_pkg.__path__):
    _mod = importlib.import_module(f"{_pkg.__name__}.{_info.name}")
    for _name, _obj in vars(_mod).items():
        if _name.startswith("_") or isinstance(_obj, ModuleType) or not _name.endswith("_tl"):
            continue
        assert globals().get(_name, _obj) is _obj, f"backend symbol collision: {_name}"
        globals()[_name] = _obj

构建

必须先 export DEEPINFER_ACCELERATOR=nvidia|ascend，再 ./build.sh：装对应 requirements（NVIDIA 还要把 NCCL 钉到 2.32.3）， 逐个从 vendor/ 打 wheel 并安装，最后编出唯一的原生扩展 deepinfer._C（子模块 engine、cuda_utils、graph_timer）。 .so 被软链进 deepinfer/_so/<accel>-<arch>/，__init__.py 把它加进 __path__，所以两个平台的构建产物能共存在一棵源码树里。

绑核

每个 worker 先按 GPU 所在 NUMA 节点绑 CPU 和内存（NVIDIA 读 sysfs，Ascend 解析 npu-smi 拓扑）， 再把进程钉到连续的物理核区间 [gpu_id·n, (gpu_id+1)·n)。多模态预处理进程绑在同 NUMA 节点的超线程兄弟核上，避开主进程的核。

算子清单

43 个 TileLang 内核，大多是让数据别回 CPU 的胶水

每个算子由三部分组成：顶层文件是接口加 PyTorch 参考实现加测试，cuda/ 和 asc/ 各有一个返回编译后内核的 *_tl 工厂。 cuda 有 43 个，asc 有 42 个，只缺调试用的 detect_outlier_and_abort_tl。Ascend 另有寄存器内 BF16 KV 量化与补偿 RSQRT 两个私有辅助模块。

模型侧的组织方式

参数容器与运行时适配器分开

v4_modules/__init__.py 把文件分成四种角色：参数容器只描述 HF 名字、形状、dtype，没有 forward； 运行时适配器包住容器，把权重合并、重排成运行时布局并持有 forward，之后用 untyped_storage().resize_(0) 释放原件； 无参数算子；由 config 推出的拓扑与组装（cross_layer、builder）。整棵树先在 meta 设备上建出来，路由专家直接以打包好的 FP4 落盘格式分配。

投影按「输入来自哪里」合并：[Wq.A | Wkv.A] 一次 GEMM，[Wq.B | indexer q_B] 一次 GEMM，压缩门、压缩 A 与 indexer 权重一次 GEMM。 mHC 的 post 被延迟到下一个子层，与它的 pre 融合成一次 mega_mhc。 模型本身的结构（CSA2 四种注意力层、mHC、Engram、DSpark）见 V4.1-Flash 解剖页。
