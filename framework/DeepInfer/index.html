DeepInfer 框架解剖

DeepSeek 开源的推理框架，线上撑着 V4.1-Flash 的大规模服务。开源出来的是一个离线推理引擎： Python 管编排，C++ 管调度，两万多行 TileLang 写胶水内核，重算子交给 FlashMLA、DeepGEMM、DeepEP、DeepSelect。 它只服务一个模型，几乎每个设计都为这个模型定做：滑窗加压缩 KV、块并行草稿、四路 mHC 残差。 这组页面按「整体结构 → 关键模块 → 关键 feature → 优势」把代码读一遍。

先划清范围

开源的是引擎，不是整套服务

README 写明完整服务还缺三样：KV cache 系统、VE / Prefill / Decode 拆分、数据并行副本间的负载均衡， 并说明「需要的引擎功能大部分已经实现」。代码里对应的是一组空的虚函数和 C++ 侧的 fork、pin、状态清零接口。 LLMEngine 的 docstring 也写着「This release does not include an online-serving wrapper」。

开源版里有

  • 离线入口 LLM.generate()；三种引擎 NORMAL / PROMPT / COMPLETION（后两种是 PD 拆分时的角色）
  • C++ 调度器、块管理器、序列状态机、输入元数据准备
  • 零开销异步调度（ZOS），默认打开
  • DSpark 块并行草稿 + 置信度调度验证
  • SWA 有界重放（YOCO prefill 截断）
  • Attention DP、镜像 CP、MoE EP + EPLB
  • 批不变推理、确定性采样、结构化输出
  • 视觉塔：开源版里和 LLM 跑在同一个引擎内

不在开源版里

  • 在线 HTTP 服务、Entrypoint、Prefill / Decode / VE 三种负载均衡器
  • 自动前缀缓存与 KV 落盘：每次调度都传 num_cached_tokens_gpu=0，只留了 do_save_kvcache 等空钩子
  • PD / VE 拆分的子类实现：init_pd_split、send_processed_prompts 都是空函数
  • 协议转换 deepseek-recipe：另一个仓库
  • 停止字符串、beam search、n>1、min-p 和各类重复惩罚

线上是什么规模

仓库自带的 doc/inference_deployment_qa.md 给了背景：单集群每天 155 万亿 token，谷时价每 GPU 小时收入 38 美元。 prefill 跑在普通 8 卡机上（EP2–8 / DP2–8，取显存允许的最小值），decode 跑在超节点上（EP64–128 / DP64–128 的 Wide-EP）。 KV 保留 72 小时以上。生产环境不用 TP，也不用 CP。

整体结构

七层：调度、块管理、输入准备都在 C++ 里

从上往下是调用方向。Python 侧只在 step 之间编排：调哪个 worker 方法、什么时候后处理、什么时候释放。 「这一步谁上车、每条序列算多少 token、KV 写到哪个槽」都由 deepinfer._C.engine 决定， 并且直接写进 pinned 张量，Python 不逐条遍历序列。

进程拓扑

一个 DP rank 就是一个引擎进程，没有中心调度器

引擎进程自己就是 driver worker（cp_rank 0），不为本卡另起进程（llm_engine.py:368-414）。 只有 CP>1 时才 spawn cp_size−1 个从进程。从进程阻塞在 start_slave_worker_loop 里， 从共享内存队列收 (method, kwargs) 再执行。调度结果不发给从进程：driver 把它变成 InputMetadata， 非张量字段走 shm 队列，CUDA 张量走 NCCL broadcast。

各 DP rank 的 C++ Scheduler 各排各的，只在两处同步。一处是投票决定这一步全组做 prefill 还是 decode（ZOS 打开时走 gloo CPU 组）； 另一处是 MoE 层的 EP 通信。model_parallel_size 直接等于 cp_size（config.py:171）， 所有稠密投影都是 ReplicatedLinear。部署文档的说法是沿用 V3/R1：attention 走 DP，DP 数等于 EP 数。

一个 step

「forward 当前步 → 后处理上一步 → 采样当前步」

Worker.execute_model_step 是唯一的执行入口：prefill、decode、ZOS 开或关、占位空步，都走同一轮。 顺序上的关键是第 2 步：上一步的后处理被夹在本步 forward 和本步采样之间， 这样 CPU 后处理和 GPU forward 并行。详见第 2 章 ZOS。

先给结论

它的优势来自「只服务一个模型」

热路径上没有 CPU 气泡

调度在 C++、释放 GIL；ZOS 让 CPU 永远领先 GPU 一步；forbid_cuda_sync 把「热路径不准同步」变成运行时报错。

模型结构直接变成引擎能力

压缩 KV + 滑窗让 KV 小到可以跨机房搬；YOCO 结构让解码层只重放最后 140 个 token；DSpark 的置信头直接喂调度器。

投机解码是无损的，且可调度

真拒绝采样（带误差界证明），草稿长度由「期望接受数 ÷ 实测图耗时」逐步优化，不是固定 5 个。

确定性是一等公民

采样器用定点原子和计数器 RNG，批不变开关覆盖 GEMM / MoE / mHC / FlashMLA，并有「批量跑 vs 单条跑逐位相同」的测试。

完整的优势、代价与对照在 第 6 章。
