第 3 章 块池 + 状态槽 SWA 有界重放 FP4 / MXFP8 KV

KV 缓存与有界重放

V4.1 的 KV 分成两类：随上下文增长的压缩 KV，和长度固定的滑窗 KV 加压缩中间态。 DeepInfer 用两块独立的裸显存分别装它们，并利用模型的 encoder / decoder 分层， 让后 20 层在 prefill 时只重算最后 140 个 token。这一章读 worker/cache_engine.py、 tilelang_ops/cache_common.py 和 YOCO 相关代码。

128token / 块
288 B主 KV / token（FP4，默认）
528 BSWA / token（MXFP8）
68 Bindex K / token（MXFP4）
134SWA 环槽数 = 128 + 6
140解码层 prefill 只重放的 token 数

关键 feature · 两块裸显存

块池装会变长的，状态槽装不会变长的

CacheEngine 只做两次分配，都走 _C.cuda_utils.alloc_tensor（直接 cuMemAlloc），不经过 torch 的 caching allocator。 块池按 128 token 一块分页，块内按层切片；状态槽每条序列一个，大小固定，与上下文长度无关。 两边各有一个 C++ BlockManager：空闲链表加引用计数，fork 出的序列靠 pin 共享块。

缓存格式

三种低精度格式，按用途分开选

MLA 只有一个 KV 头，latent 是 512 维（448 维 NoPE + 64 维 RoPE），所以「每 token 字节数」就是整层的 KV 开销。 部署文档的「低精度」一节给出了这三处 FP4 的取舍，代码里的格式定义在 cache_common.py。

缓存放在默认格式B / token说明
swa_cache状态槽MXFP8：512 × e4m3 + 每 32 个一个 ue8m0 scale528环形，W + B 个槽；decode 时由融合内核 norm + RoPE + 量化后直接写入
ca_cache块池FP4 e2m1，每 16 个一个 e4m3 scale（类 NVFP4，无全局 scale）288use_fp4_sparse_kv 默认 True（hugging_face/config.py:303）；可退回 MXFP8，528 B
ica_cache块池MXFP4：e2m1 + 每 32 个一个 ue8m068indexer 的 K，128 维；只有写 KV 的 owner 层有

启动日志会打印实际选中的格式（deepseek.py:459-460）。fused_transform 里有 Hadamard 变换选项，但模型代码没有调用方传入 HadamardArgs。

显存预算

先假跑一遍，再把剩下的全给块池

  1. profile_run 模拟 max_num_seqs 条序列跑一次 forward。prefill 引擎把 token 预算摊给它们，并让 0 号序列的 seqlen_k 取到最大长度；decode 引擎每条 1 + nextn 个 token。期间分配一份临时的真 KV，并把 DEEPINFER_FORCE_IMBALANCE_RATIO 设为 1.8，模拟 MoE 负载不均时的峰值（model_runner.py:444-512）。
  2. 可用量 = 总显存 × 0.9 − 峰值（torch 分配 + 非 torch 分配）− 2 × 状态张量大小。代码注释说 2 倍是「state store & copy buffer」（base.py:242），而 CacheEngine 实际只分配一份。
  3. 块数在整个 world 上 all-reduce 求和、除以 world size、向下取偶（base.py:264-266），即平均值。_init_cache 的 docstring 写的是「取最小值」，与代码不符。
  4. 引擎要求 128 × 块数 × 0.8 ≥ runtime_max_model_len，否则启动失败。

前缀复用

开源版没有自动前缀缓存，只留了注入口

每次调度都传 num_cached_tokens_gpu=0，所以统计里的 prefill_caching_rate 恒为 0。 能用的复用手段只有两个：fork_seq（pin 住父序列的块和状态槽，分支 id 以 _ 开头表示「待 fork」）， 以及 num_cached_tokens setter（注释：「外部注入的命中数」）。examples/benchmark.py 就是用 fork 构造「先算一条长前缀，再分出 N 条」的场景。

生产环境的 KV 系统没有开源，部署文档描述了它的形状。理解这个形状，才能理解为什么状态槽要分「可落盘」和「丢弃」两段：

KV 类型放在哪怎么取回
在途的块 KV、状态 KV推理 GPU 显存—
SWA KV（存储区那 1.35 MiB）产生它的那台机器的主存，单副本，不进 3FSEntrypoint 机器上有一张按 key 分区的内存目录记录它在哪；跨机命中走 400G VLAN 拉取
分页的块 KV独立的 3FS 集群，10+2 纠删码，约 100 PiB SSDEntrypoint 先做哈希链前缀匹配（这一步无法隐藏）；3FS → 主存由独立进程异步拉；主存 → HBM 用 GDR，逐层与 forward 重叠

为什么用独立存储集群

这样每台 prefill 机器都能命中任意前缀，前缀亲和与负载均衡不再冲突；存储扩缩容与计算解耦；计算节点故障率高一个数量级以上，存储也不受影响。

保留多久

kvcache-store 自身没有 TTL，回收全靠 3FS 的 GC。agent 流量 3 天，chatbot 7 天。chatbot 的长尾更重：经验上 TTL 缩到 3 天会损失 0.5%–1% 的命中率。decode 不开 KV offload，但 decode 产生的 KV 仍写盘，用来提高命中率。

关键 feature · SWA 有界重放

解码层在 prefill 时只算最后 140 个 token

V4.1 的 40 层在 DeepInfer 里被分成两段：n_prefill_layer 之前是「编码层」，之后是「解码层」（YOCO consumer）。 n_prefill_layer 取第一个压缩比为 1 的层的下标（hugging_face/config.py:158），V4.1 是 20，层 20–39 是解码层。 关键约束在 cross_layer.py：解码层里写 KV 的 owner 层，其压缩 KV 和 index K 是从边界处的同一份 hidden （shared_hidden，第一个解码层 attn-norm 之后的输出）投影出来的，而不是从各自的 hidden。 所以解码层的块 KV 只依赖编码层的计算，可以按全长精确写出。真正要逐层算的只剩解码层的 SWA。

DEEPINFER_YOCO_PREFILL_TRUNCATION_MODE行为用途
off（默认）解码层照常全长计算精确，代价最高
mask保留全部 query 行，只把解码层 SWA 的可见区收窄到截断矩形不省计算，用来和 compact 做逐位对拍
compact在边界层换成 get_consumer_view()：每条序列只留最后 KEEP_TOKENS 行（每个 chunk 至少 1 行），hidden、mHC 残差、top-k、候选块都 gather 到紧凑行上（CP>1 时先 all-gather）README 推荐配置：compact + KEEP_TOKENS=140

为什么下界是 W + B

C++ 强制 keep_tokens ≥ window_size + max_backtracking_tokens（prepare_tensor_input_v4.cpp:355）， 注释是「截断范围要 ≥ window size + 回退 B，要保证回退后仍然有 window size 个」。 投机解码被拒时序列最多回退 B = nextn + 1 = 6 个位置，回退之后解码层的 SWA 环里仍要有一整窗有效 KV。 128 + 6 = 134；推荐值 140 比下界多 6 个，代码和文档都没说这 6 个的用途。

命中策略随之改变

文档的规则是「命中长度由块 KV 决定，最后一块要不要重算由 SWA 决定」。 长度 L 的输入最多命中 L − 134。先查块 KV 得到 L1（128 的倍数）；若 [L1 − 128, L1] 里有 SWA 存档就命中 L1，否则命中 L1 − 128，并重放最后 128 个 token 重建编码层 SWA（encoder 侧的有界重放）。

它对其他模块的约束

compact 模式下 DeepEP dispatch 关掉 do_cpu_sync（mlp.py:485）；Engram 层必须在编码层里（deepseek.py:136）； DSpark 的目标层必须全部落在边界同一侧。开着截断时，代码注释允许「抢占导致的结果变化」（llm_engine.py:888）， 因为重算时 SWA 是重放出来的近似值。

怎么验证没算错

mask 与 compact 两级对拍

L1 · 单卡，几秒，不要权重

examples/yoco/yoco_equiv.py mask-compact 比较两种模式下的 SWA pivot、可见 key、写入槽位、压缩 key 范围，元数据必须完全一致。

L2 · 8 卡，真 checkpoint

run_yoco_equiv_l2.sh 固定 teacher-forcing 轨迹，逐元素比较 logprob 和 top-K。加 --mtp N 时还逐位比较 DSpark 的置信度，用来直接检查 DFlash 主缓存。
