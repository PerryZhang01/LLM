性能与优势

前四章讲机制，这一章收尾。先看仓库自带的性能曲线和精度参考值，再总结 DeepInfer 的优势和代价， 和 vLLM 一类通用引擎对照，列出读代码时遇到的注释与代码不一致之处，最后给一条读码路线。

Wide-EP 买到了什么

同为每 rank 64 并发，EP64 比 EP8 的每卡吞吐高约 24%（15.8k 对 12.7k），每用户速度也高约 24%（246 对 198）。到 256 并发两者趋近（26.3k 对 24.9k）。部署文档的解释是：EP 越宽，每张卡每步要读的专家权重越少。

精度参考值（eval/README.md）

默认配置下 Pass@1：AIME 2026 99.9%（30 题 × 32 样本），GPQA Diamond 93.4%（198 题 × 8），HLE-Full 42.6%（2,500 题，其中 342 道带图）。生成与打分分两步，HLE 不允许规则打分，因为一半以上是自由文本答案。

优势

八条优势，前四条是这个框架独有的

1 · 热路径上没有 CPU 气泡

调度、块管理、输入准备都在 C++ 里并释放 GIL；输出走对象池和指针。ZOS 让 CPU 领先 GPU 一步，下一步的 input_ids、seqlens 和 decode 元数据都在 GPU 上算。forbid_cuda_sync 把「热路径不准同步」变成运行时报错。第 2 章

2 · 投机解码可调度，且无损

DSpark 一次 forward 出整块草稿。置信头把「这个草稿会不会被接受」直接交给调度器，调度器按实测的图耗时挑出期望吞吐最高的验证量。验证是带误差界证明的拒绝采样。生产工作点 +5.4%。第 4 章

3 · 模型结构直接变成引擎能力

MLA 单头 + FP4 压缩 KV，主 KV 每 token 288 B。状态槽按「可落盘 / 丢弃」分区，配合 YOCO 让解码层只重放最后 140 个 token，部署文档称这几乎砍掉一半 prefill 计算。KV 小到能跨机房做 PD 拆分（文档估算每 8 卡约 400 Gbps）。第 3 章

4 · 确定性是设计目标，不是补丁

采样器用保序键 radix select、定点整数原子累加、按位置生成的计数器随机数；批不变开关覆盖 GEMM、MoE、mHC、FlashMLA。测试要求批量跑和单条跑的 token 与 logprob 逐位一致。第 4 章

5 · Wide-EP 与融合 MoE

没有 TP，attention 全 DP；NVLink 域内一个 mega_moe 内核做完 dispatch 到 combine；EPLB 在域内用 symm_mem 直接拉权重。生产 decode 跑 EP64–128，moe_lb 1.09。第 5 章

6 · 一套代码两种硬件

后端选择只在 ops.py 一个文件里。43 个 TileLang 内核在 cuda 和 asc 上各有一份（缺一个调试内核）；两个平台的构建产物可以共存在同一棵源码树里。

7 · 可测、可对拍

每个 TileLang 算子都带 PyTorch 参考实现和 pytest；YOCO 的 mask / compact 两级对拍；采样器用 KS + PIT 检验分布；同步守卫有交错退出与并发压力测试。

8 · 生产验证过

部署文档给出单集群每天 155 万亿 token、谷时每 GPU 小时 38 美元收入；整体负载均衡达到完美均衡离线基准的约 80%。开源版的内核与内部版端到端差距 ≤ 5%。

代价与边界

这些优势都以「只服务一个模型」为前提

模型绑定很深

只支持 DeepSeek-V4.1-Flash。压缩比只允许 0 / 1 / 2，代码明确报错「C4 and C128 have been removed」；KV 格式、状态槽分区、YOCO 边界、DSpark 都按这个模型写死。换模型基本等于重写模型层和一半的元数据内核。

离线引擎，不是服务

没有 HTTP 服务、自动前缀缓存、PD 拆分实现和负载均衡器。生产里真正决定命中率和尾延迟的那部分（3FS KV 存储、三种 LB）不在仓库里。

不混批的代价

decode 要定期停下来给 prefill 让路。推断：在 NORMAL 引擎里，一条新请求可能要等到下一个 ALL / ANY 投票点（最多 70 / 100 个 decode 步）才开始 prefill。生产上靠 PD 拆分避开这个问题，开源版没有拆分。

功能面窄、硬件门槛高

采样没有 min-p、重复惩罚、停止字符串、n > 1。硬件只支持 SM100 和 Ascend 950；要 CUDA 13、GCC ≥ 13、Python 3.12。批不变只在 NVIDIA 上可用，NPU 侧还有多处 TODO(NPU) 临时补丁。

取舍对照

和 vLLM 一类通用引擎比，选择都反过来

README 致谢里说 DeepInfer「最初主要基于 vLLM 构建」，并参考了 SGLang 与 TensorRT-LLM。shm_broadcast.py 等文件仍能看出出处。但几个关键取舍都和通用引擎相反：

维度DeepInfervLLM（V1 引擎）的常见做法
调度器C++，释放 GILPython
批组成每步只做 prefill 或只做 decode，DP 组投票统一prefill 与 decode 混在同一批（chunked prefill）
模型并行没有 TP；attention DP + 专家 EP，prefill 可选 CP以 TP 为主，另有 DP / EP / PP
前缀缓存开源版没有；生产用外置 3FS 集群 + 主存里的 SWA 目录内置的按块哈希自动前缀缓存
投机解码块并行草稿 + 置信度驱动的变长验证EAGLE、MTP、n-gram 等，验证长度按配置固定
异步调度默认打开，下一步的 input_ids 在 GPU 上 gather可选项
确定性采样器按位置生成随机数，批不变开关覆盖到 attention 与 MoE依赖具体后端与配置
模型覆盖1 个数百个架构

读代码时的坑

注释与代码不一致的七处

以下都以代码行为为准。对改代码的人来说，相信注释就会出错。

位置注释或文档说代码实际
scheduler.hpp:556block 不足时「抢占 output 最短的 seq」running 按输出长度降序排，牺牲者取 running[l]，即输出最长的。FINISHED_PREEMPTED 的注释「终止占用 KV 最多的任务」与代码一致
llm_engine.py:427「take the minimum number of blocks across all workers」base.py:264-266 是 SUM ÷ world size 再向下取偶，即平均值
hugging_face/config.py:159第一个 ratio == 1 的层「和它之前的层构成 prefill 侧」返回的是该层下标；layer_id ≥ n_prefill_layer 才是解码层，所以这一层本身属于解码层（它也是第一个解码层里的 KV owner）
layers/sampler.py:65应用「temperature、top-k / top-p / min-p」没有 min-p，SamplingParams 也没有这个字段
README.md:26异步调度「Enabled by default」环境变量默认 False；只有经 EngineArgs 时才对 NORMAL / COMPLETION 设为 1。走 LLM() 时确实默认开
worker/base.py:242「state store & copy buffer，所以要开两倍大小」预算扣了两倍，CacheEngine 只分配一份；另一份的用途在开源代码里看不到
v4_modules/heads.py:86config 里有 dspark_block_size运行时草稿块大小取 DEEPINFER_USE_NEXTN_DECODE，没看到与 config 值的校验

读码路线

按数据流读，十二站

  1. README.md + doc/inference_deployment_qa.md：先知道每个设计为什么存在
  2. deepinfer/_C/engine.pyi：735 行的类型桩，一眼看清 C++ 暴露了什么
  3. engine/llm_engine.py：step()、_process_model_outputs、post_process、虚函数钩子
  4. worker/worker.py：execute_model_step 的四步，和 _correct_seqlens_qk
  5. csrc/engine/scheduler.hpp：_schedule（投票）、_schedule_prefill、_schedule_decode、process_outputs
  6. csrc/engine/zos.cpp + input_metadata/prepare_tensor_input_zos.py：ZOS 的 remap 与 GPU 侧输入
  7. worker/model_runner.py + cuda_graph_runner.py：发射、图的分档与回放
  8. models/deepseek.py → decoder_layer.py → v4_modules/attn.py：整网 forward、YOCO 视图切换、四种 attention
  9. models/mtp/dflash.py + layers/sampler.py + csrc/engine/mtp_varlen.hpp：DSpark 全链路
  10. worker/cache_engine.py：先读 KVCache 与 StateBlock 的 docstring
  11. v4_modules/mlp.py + model_executor/eplb/：两条 MoE 路径与专家重排
  12. tilelang_ops/ops.py，再挑一个算子的顶层文件，看参考实现与测试怎么写
