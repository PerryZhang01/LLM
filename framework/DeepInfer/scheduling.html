第 2 章 C++ Scheduler ZOS CUDA Graph

调度与执行

DeepInfer 让 GPU 不等 CPU，靠三件事。调度写在 C++ 里并释放 GIL； 下一步在上一步的结果出来之前就排好、发射出去；热路径上任何会同步的操作都会直接报错。 这一章按这条线读 csrc/engine/ 和 deepinfer/worker/。

195默认抓的 decode 图（按 total_q）

调度核心

调度器在 C++ 里，Python 只拿指针

csrc/engine/scheduler.hpp 1329 行，加上序列、块管理、MTP 变长、输入元数据准备，一共 5.2k 行 C++，经 pybind11 暴露成 deepinfer._C.engine。 值得注意的不是「用了 C++」，而是它如何避免和 Python 互相拖累：

不占 GIL

  • _schedule 在 py::gil_scoped_release 下运行（scheduler.hpp:276，注释：「否则会阻塞其他 python 线程」）
  • build_request_outputs、prepare_sampler_inputs、prepare_zos_inputs、free_seq 等同样释放 GIL
  • 块管理器的锁 Lockable 断言调用时不持有 GIL，用带 20 秒超时的 error-checking mutex，防止死锁变成静默挂起

不造 Python 对象

  • SequenceMetadata 来自对象池，placement-new 复用（object_pool.hpp）
  • RequestOutputPool 固定 10,000 槽，输出以 uint64 指针数组穿过 Python，下一步自动回收
  • process_outputs 等返回借用函数内 static vector 的 numpy 数组，注释要求「下一次调用前用完」
  • DeferredRelease 把池化对象的释放推迟一步，因为 ZOS 下 GPU 可能还在读

关键 feature · 步型统一

一步只做一件事，DP 组靠投票统一步型

SchedulerOutputs.prompt_run 只是一个 bool，prepare_sample.cpp:61 直接断言 「Mixed prefill and decode batches are unsupported」。不混批的代价是 decode 要偶尔给 prefill 让路； 换来的是 decode 步的形状只取决于 total_q，可以整步进 CUDA Graph。

麻烦在 DP：各 rank 的调度器独立，但 MoE 层的 EP 通信要求全组同一步做同一种事。代码注释原话是「dp 内必须同型，靠投票统一」。 NORMAL 引擎默认做 decode，只在两类投票点上考虑 prefill：

投票点间隔（环境变量 · 默认）规则为什么
ALLDEEPINFER_PREFILL_ATTEMPT_INTERVAL · 70全员都想 prefill 才做（allreduce MIN）防止一个 rank 干活、其余 rank 陪跑空 prompt step
ANYDEEPINFER_PREFILL_ANY_ATTEMPT_INTERVAL · 100任一 rank 想做就全组做；与 ALL 点重合时按 ANY给孤立 rank 兜底：它的 prefill 最多等 100 个 decode 步

「想做」的定义是 KV 占用 ≤ 0.9（GPU_CACHE_PREFILL_WATERMARK）且 waiting 队首可调度。 投票通过后还有第二轮投票，确认真有 rank 排出了 prefill；全组都空手就退回 decode。 排到 prefill 的 rank 正常做，没排到的 rank 跑一个空 prompt step「陪跑」。 

// scheduler.hpp:307-340（节选，注释原文）
bool is_any_point = (decode_step != 0) && (decode_step % prefill_any_attempt_interval == 0);
bool is_all_point = (decode_step % prefill_attempt_interval == 0);
if (!is_any_point && !is_all_point) return _schedule_decode(acquire);
bool want = (get_gpu_cache_usage() <= GPU_CACHE_PREFILL_WATERMARK) && _has_prefill_waiting();
...
// 第二轮投票：确认这轮真有 rank 排出了 prefill。want 只看了 waiting 非空，
// 但 _schedule_prefill 仍可能空手（slot 满、KV 块不够）。
// 全组都空手时必须转 decode：硬做空 prompt step 会把 decode_step 清零，
// 下一步接着投票、接着空手——running 满 + waiting 非空就死循环了。
bool any_scheduled = (_dp_allreduce(outputs ? 0 : 1, c10d::ReduceOp::MIN) == 0);
...
// 组内确有 rank 在做 prompt：本 rank 陪跑空 prompt step 保持步型一致
return _make_outputs({}, true, 0, {}, {}, {}, 0);

一个细节

prompt step 会把 decode_step 清零，而 0 恰好是 ALL 点。所以做完一次 prefill 后， 只有全员都还有 prefill 活才会接着做，不会出现一个 rank 拖着全组连做 prefill 的情况。 PROMPT 引擎只做 prefill，COMPLETION 引擎只做 decode，这两种都不投票。

准入与抢占

prefill 先到先得，decode 抢输出最长的

prefill 准入（_schedule_prefill，按顺序检查）

  1. 长度：超过 prompt_limit 记为 FINISHED_IGNORED
  2. KV 一次分够：块和状态槽一起检查，整条序列的块在首次调度时全部分配，即使之后分块 prefill
  3. 序列数：与 running 合计不超过 max_num_seqs（默认 256）
  4. 注意力预算：Σseqlen_k ≤ DEEPINFER_PREFILL_MAX_SUM_SEQLEN_K（默认不限）
  5. token 预算：max_num_batched_tokens，分块长度对齐到 2·cp（镜像 CP 要求）
  6. 边界：图像不能被切开（_adjust_chunk_size）；外部可强制 chunk_checkpoints

遇到第一条排不下的就停，不跳过去找后面的。chunked_prefill 默认关闭；打开后 NORMAL 模式每步最多一条被切分的序列，且放在最后。

decode 调度与抢占（_schedule_decode）

  • 先把 prompted 队列（prefill 完、或 fork 出来的序列）接入 running；fork 的序列对状态槽和最后一个半满块做写时复制
  • running 按输出长度降序排，从输出最短的一端开始分块，每条至少要一个空闲块
  • 块不够时从输出最长的一端挑牺牲者（running[l]）
  • 牺牲者默认重算：重置后推回 waiting 队首，释放块。stop_preempted_request 打开时（EngineArgs 默认打开，LLM() 默认关闭），或请求带结构化输出时（无法重算），直接以 FINISHED_PREEMPTED 结束
  • 没有 swap 到 CPU（SWAPPED 状态存在但没人用），没有优先级
# 序列状态机（sequence.hpp:30-43）
WAITING ──▶ RUNNING ──▶ FINISHED_{STOPPED, LENGTH_CAPPED, ABORTED, IGNORED, PREEMPTED, SO_FAILED, VE_FAILED}
   ▲  │         │
   │  └─ 分块 prefill 的中间块：仍是 WAITING，process_outputs 把它推回 waiting 队首
   └──────── 重算式抢占：RUNNING → WAITING

# MtpState（草稿 token、接受率、info_slot、schedule_cnt / process_cnt）、StructuredOutputState

关键 feature · 零开销异步调度（ZOS）

CPU 永远领先 GPU 一步

朴素的流水是 schedule → forward → sample → 后处理，后处理前要等 GPU 把采样结果拷回来。 这段时间加上下一步的调度，GPU 是空的。部署文档说明 ZOS 参考了 SGLang 和 NanoFlow 的做法： GPU 在跑 forward(N) → sample(N) 时，CPU 同时跑 schedule(N+1) → launch_forward(N+1) → 后处理(N−1) → launch_sample(N+1)。

N 的结果还没出来，N+1 怎么排

难点在于：调度 N+1 时，N 采到哪个 token、接受了几个草稿、下一轮草稿置信度多少，CPU 全都不知道。 DeepInfer 的办法是CPU 只按上界排，确切值留在 GPU 上算：

CPU 不知道的做法代码
N 接受了几个 token，所以 seqlen_k 不确定CPU 悲观记账：每条在途步记 nextn+1 个 token，块也按全部接受预留。GPU 上 seqlens_k += seqlens_q − (nextn − 上一步接受数[remap])scheduler.hpp:726 · compute_seqlens_k_zos.py:10-32
N 采到了哪个 token，所以 input_ids 不确定CPU 不填。C++ prepare_zos_inputs 只给出 remap[i] = 本批第 i 条在上一批里的下标（顺序没变时走快路径）。GPU 上第 0 位取上一步采样的 token，第 j 位取上一步的第 j−1 个草稿zos.cpp:172-226 · gather_input_ids_zos.py
N 的置信度，所以每条验证多长不确定CPU 只定总量 total_q（也就决定了用哪张 CUDA Graph），按请求的分配在 GPU 上用最新置信度重算，见第 4 章schedule_mtp_varlen.py
Engram 的 n-gram 窗口同样从上一步设备端的采样与草稿结果拼出来gather_engram_tokens_zos.py
decode 元数据（位置、槽位、索引）C++ 只抽出每条序列的紧凑数组；一个 TileLang 内核 prepare_v4_decode_metadata 把全部 decode 元数据直接写进 CUDA Graph 的输入缓冲prepare_tensor_input_zos.py · prepare_v4_decode_metadata.py
采样前 CPU 需要确切的 seqlensGPU 算出的 seqlens_q 拷回 pinned 缓冲并记一个事件；采样前 update_metadata_for_sampling_zos 等这个事件，再刷新 last_output_token、草稿槽、SO 状态worker.py:146-152 · zos.cpp:309-335
N 已经 EOS 的序列N+1 可能还会被 forward 一次，结果丢弃。它的块要等到 GPU 越过那一步之后的 pre_sampler_sync 才释放zos.cpp:328 · llm_engine.py:67-119

默认打开，但开关藏在 EngineArgs 里

环境变量 DEEPINFER_ZERO_OVERHEAD_SCHEDULING 本身默认 False（environ.py:186）。 EngineArgs.__post_init__ 按引擎类型 setdefault：NORMAL 与 COMPLETION 为 1，PROMPT 为 0（engine_type.py:16）。 直接构造 LLMEngine、不经过 EngineArgs 时就是关的。

代价

块按全接受预留，在 KV 紧张时会更早触发抢占。runtime_max_model_len 为 ZOS 额外多留 nextn+1 个位置（config.py:11-16）。 已经 EOS 的序列会被多算一次。关掉的方法：DEEPINFER_ZERO_OVERHEAD_SCHEDULING=0，此时改用非 ZOS 的 prepare_decode_v4。

关键 feature · 热路径守卫

「热路径不准同步」是运行时检查，不是约定

model_runner.py 的 forward 和 sample 两个发射函数都标着「IMPORTANT: This function must NOT contain any cuda synchronize」（:317、:346）， 并且确实用 forbid_cuda_sync() 包住：它把 torch 的 sync debug mode 设成 error， 任何阻塞拷贝、.item()、stream 或 device 同步都会直接抛异常。 

# deepinfer/utils.py（节选）
class _SyncDebugArbiter:
    """torch 的 sync debug mode 是进程级全局开关（C++ 静态单例），无法真正按线程生效；
    这里按线程记 intent 栈（线程内内层覆盖外层），全局模式由各线程栈顶合成：
    任一线程 allow 即放行（宁漏报不误杀），否则有 forbid 即报错，全空还原基线。"""
    def _apply(self) -> None:
        tops = [s[-1] for s in self._stacks.values()]
        if not tops:          mode = self._baseline
        elif "allow" in tops: mode = "default"
        else:                 mode = "error"
        torch.cuda.set_sync_debug_mode(mode)

def forbid_cuda_sync():
    """torch.cuda.Event.synchronize is NOT covered by torch's sync debug mode, so intentional
    event-based sync points (e.g. in ZOS) are unaffected."""

为什么要「仲裁者」

开关是进程全局的，而引擎进程里有其他线程（SO 编译、统计日志、profiler）会合法地同步。 如果每个 scope 各自保存、恢复旧值，两个线程交错退出时会把 error 泄漏给别人。 测试 tests/test_cuda_sync_guards.py 专门复现了这个旧 bug，并跑 3 秒随机压力测试， 断言「任何线程在自己的 allow 里都不会看到 error」。

ZOS 的合法同步点从哪走

ZOS 需要等上一步采样结束，用的是 torch.cuda.Event.synchronize()，它不在 sync debug mode 的覆盖范围内。 所以「刻意的同步」和「意外的同步」在机制上就分开了。 调试时可以用 DEEPINFER_DISABLE_SYNC_GUARD=1 整体关掉，比如要在 forward 里打印张量。

关键 feature · CUDA Graph

decode 图按 total_q 抓，prefill 永远 eager

use_cuda_graph = not DEEPINFER_ENFORCE_EAGER and engine_type != PROMPT，而且只在 decode 步回放（model_runner.py:73, 182）。 因为有投机解码，一条序列一步可能验证 1 到 6 个 token，所以图按总 query token 数分档，而不是按请求数。

图内计时

_C.graph_timer 把一对 ping-pong CUDA 事件换进已经抓好的图的事件记录节点里， 回放时就能量出图内某一段的耗时（csrc/graph_timer/）。置信度调度用的 forward / sample 实测耗时就是这么来的。NPU 上暂不支持。

decode 性能曲线

打开 DEEPINFER_ENABLE_MTP_VARLEN 时，warm-up 会把每张图回放 1 + 5 次，去掉最大最小取均值，再在 EP 组内平均， 得到 [(graph_tokens, ms)] 交给 C++ 调度器。曲线按模型、档位、dp/cp/ep 的 sha256 缓存到 DEEPINFER_DECODE_PERF_CACHE_DIR，TTL 3600 秒。

可观测性

统计、FLOPs 估计和按需 profiler

StatsLogger

每 100 步打一次：SPS、TPS、各位置草稿接受率、平均验证长度、置信度误差、MoE 负载比、KV 与状态槽占用、TTFT、MFU。日志行先进队列，主线程不碰 logger 的锁。

FlopsEstimator

按 FP8 当量估每步 FLOPs（压缩注意力、SWA、indexer、MoE、mHC、Engram、logits，含 YOCO 截断），只用于统计和 MFU，不参与调度。LLM() 默认关统计，所以离线跑时它不运行。

profile server

DEEPINFER_PROFILE_HTTP_ENABLE=1 后每个 driver 起一个 FastAPI 线程（端口 6070 + gpu_id），POST /profile?num_steps=20 在 step 边界启停 torch profiler，因为 kineto 绑线程。
